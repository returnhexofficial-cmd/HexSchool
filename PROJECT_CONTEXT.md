## 1. Current Architecture

- Two repos: `hexschool-frontend` (Next.js 16, TS, App Router, Turbopack), `hexschool-backend` (NestJS 11, TS). (Product branded HexSchool; DB/bucket keep the `smis` name.)
- **ORM: Prisma 7** (owner decision in M02, replacing TypeORM). Schema in `prisma/schema.prisma`, CLI config in `prisma.config.ts`, runtime via `@prisma/adapter-pg`; migrations: `npx prisma migrate dev|deploy`. Partial indexes/CHECKs are hand-written into migration SQL (`--create-only`, then edit).
- PostgreSQL 16+ single database (team dev DB currently on Neon; compose postgres remains for local use); Redis for cache + BullMQ queues; S3-compatible object storage (MinIO in dev).
- Frontend global state: **Redux Toolkit** (owner decision in M02; roadmap originally said Zustand) — per-tab store via `StoreProvider`, typed hooks in `src/lib/store/hooks.ts`. Server state stays in TanStack Query.
- Next 16 note: middleware is `src/proxy.ts` (renamed from middleware.ts) — optimistic route guards via the non-sensitive `hs_session` hint cookie; real enforcement is always API-side.
- REST API under `/api/v1` (port 4000), Swagger at `/api/docs` (basic-auth in prod); Bull Board at `/admin/queues` (basic-auth always). Frontend dev on port 3000.
- Dev infra via `hexschool-backend/docker-compose.yml`: postgres:16 (host port **5433** — 5432 is taken by a native install on the dev machine), redis:7, MinIO (9000/9001), Mailpit (1025/8025).
- Single-school deployment now; **every business table carries `school_id`** so Module 31 can activate multi-tenancy without schema surgery.
- Docker Compose for dev (postgres, redis, minio, mailpit, backend); Nginx + Docker on Ubuntu for prod (formalized in Module 30).

## 2. Folder Structure

**Backend** — `src/modules/<name>/{entities,dto,controllers,services,repositories,guards,policies,events,jobs}` plus `src/common/{filters,interceptors,pipes,decorators,utils}` and `src/config`.

**Frontend** — route groups: `src/app/(public)` website, `(auth)` login flows, `(admin)` panel, `(portal)` student/parent/teacher, `(platform)` reserved for Module 31. Shared code in `src/components/{ui,shared}`, `src/lib/{api,validations,utils,hooks}`.

## 3. Naming Conventions

- DB: snake_case, plural tables, UUID PKs (`gen_random_uuid()`), constraint prefixes `fk_/uq_/idx_/chk_`.
- API: kebab-case plural resources (`/fee-invoices`), camelCase JSON fields.
- Code: PascalCase classes/components, camelCase functions/vars, TS enums mirroring PG enums.
- Document number patterns (all sequence-table backed, per school, gap-free in transaction): `{SCHOOL_CODE}-S-{YY}{SEQ4}` staff, `{SCHOOL_CODE}-{YEAR}{SEQ5}` students, `ADM-{YY}-{SEQ6}` applications, `INV-{YY}{MM}-{SEQ6}` invoices, `DV/CV/JV/CN-{YY}-{SEQ}` vouchers, `{TYPE}-{YY}-{SEQ4}` certificates — **per type AND per year** since M27, where `{TYPE}` resolves from a settings prefix map (`TC`/`CC`/`TS`/`PR`/`PA`/`CE`) and the counter key carries both, so a school's fourteenth transfer certificate and its second character certificate of 2026 are `TC-26-0014` and `CC-26-0002`.

## 4. Coding Standards

- Strict TypeScript both repos; ESLint + Prettier + Husky (lint, typecheck, test pre-commit).
- No `any` without justification comment; no raw SQL outside repositories; no unscoped (missing `school_id`) queries.
- Backend business rules live in services (controllers thin); pure calculation engines (results, payroll) are dependency-free and golden-tested.
- **Repository pattern:** all data access goes through per-entity repository classes extending `BaseRepository` (generic CRUD, pagination, soft-delete + `school_id` scoping, `withTransaction`). Services never touch the ORM/QueryBuilder directly; controllers never touch repositories. Flow is strictly Controller → Service → Repository.

## 7. API Conventions

- Envelope: `{ success, data, meta?, message? }`; errors `{ success:false, error:{ code, message, details? } }`.
- Pagination `?page&limit&sort=field:asc&search`; max limit 100.
- Mutations audited; `@Public()` routes are the explicit exception list; portal routes additionally pass `OwnershipGuard`.

## 8. Entity Relationship Spine

`schools` ← everything. `users` ←1:1→ `staff_profiles|teachers|students|guardians` (role-specific profile tables). **Live since M07:** `staff_profiles` (user_id unique FK, employee_id from SequenceService — its unique index deliberately IGNORES `deleted_at`, IDs never reused) + `staff_documents` (hard-deleted with their S3 object) + `document_sequences` (shared counters). Staff creation = one transaction (sequence + user + default role by designation + profile); RESIGNED/TERMINATED cascade deactivates the user via event listener (sessions revoked first). **Live since M08:** `teachers` (SEPARATE table sharing the user — not a staff_profiles extension; personal columns duplicated + salary_grade/mpo_index_no/specialization; same never-reuse employee-ID rule) with `teacher_qualifications`, `teacher_subjects` (expertise), `teacher_section_subjects` (one teacher per session×section×subject slot — upsert replaces, audit keeps history), `teacher_leaves` (interim → M21), `teacher_evaluations`, `teacher_documents`; `sections.class_teacher_id` FK now real (cap per session via `academic.max_class_teacher_sections`). **Live since M09:** `students` (permanent `student_uid` from SequenceService — its unique index IGNORES `deleted_at`, never reused; lazy `user_id`; rotatable `qr_token`; birth-cert soft-unique per school) —M:N→ `guardians` (shared across siblings, deduped by phone, lazy `user_id`) via `student_guardians` (composite PK, one primary per student = partial unique `WHERE is_primary`, promote/demote transactional); `student_medical_info` (1:1, permission-gated `student.medical.view`), `student_documents` (S3, hard-deleted with object), `student_status_history` (append-only). **Live since M11:** `enrollments` = student × session × class/section/group/shift with a roll number (all attendance/marks/fees hang off `enrollment_id`, NOT `student_id`) — one live enrollment per (student, session) and roll unique per (session, section) are PARTIAL unique indexes excluding soft-deleted + CANCELLED rows; `enrollment_transfers` (append-only section-move log); `promotion_batches` →1:N→ `promotion_items` (DRAFT→EXECUTED→ROLLED_BACK; execute closes old enrollments + creates new-session ones + graduates final-class students; `to_enrollment_id` on the item lets rollback delete exactly what it created). **Live since M10:** `admission_cycles` (session-scoped campaign, soft-unique name) →1:N→ `admission_cycle_classes` (per-class seats + fee, uq cycle+class) and `admission_applications` (applicant/guardian SNAPSHOTS — master student/guardian rows created only at conversion; `application_no` never reused; live-duplicate partial unique on cycle+class+phone+dob excluding CANCELLED/REJECTED/EXPIRED; `student_id` FK set on ADMITTED) + `admission_tests` (one slot per cycle+class). **Live since M06:** `classes`/`subjects`/`departments`/`shifts`/`groups` are session-independent masters; `sections` = class × session (identity unique incl. NULL-safe shift via COALESCE index; `class_teacher_id` FK deferred to M08); `class_subjects` defines curriculum per class × session (× optional group). **Live since M12:** `student_attendances` hangs off `enrollment_id` (never `student_id`) with `section_id` denormalized AT MARKING TIME so a mid-year transfer cannot retro-move history; identity is a partial unique over `(enrollment_id, date, COALESCE(period_id, nil uuid))` excluding soft-deleted rows (`period_id` is a bare UUID column until M13 adds periods + the FK). `staff_attendances` is polymorphic over the two employee tables (`person_type` + `person_id`, no FK, one row per person per date). `student_leave_applications` (student × session range, reusing the M08 `leave_status_enum`) — approving one rewrites recorded ABSENT/HALF_DAY days in the range to LEAVE. **Live since M14:** `exam_types` →1:N→ `exams` (session-scoped, soft-unique name, `grading_system_id` live while building + **`grading_snapshot JSONB` frozen at PUBLISH** — M15 reads the snapshot, never the live table) →N:M→ classes via `exam_classes`, and →1:N→ `exam_subjects` = the paper for one class × one subject, carrying BOTH the mark distribution (flat `full_marks`, or a CQ/MCQ/practical/CA split that must sum to it, plus nullable per-component pass **thresholds**) AND the sitting (`exam_date` + `start_time TIME(0)` + `duration_min` + `room`, all-or-nothing by CHECK). Exam sittings deliberately do **not** reference M13 `period_slots`. `seat_plans` (one room × one exam date, `uq(exam_id, date, room)`) →1:N→ `seat_plan_entries` keyed on **`enrollment_id`** — both hard-deleted, regenerated per date wholesale like `timetable_entries`. **Live since M15:** `marks` = one candidate × one paper, keyed on **`enrollment_id`** (`uq(exam_subject_id, enrollment_id)`, no soft delete — a mark is re-entered in place so its id stays stable for the correction log), carrying the four component columns, a stored `total`, `is_absent`, `grace_applied`, and `grade`/`grade_point` that **only a processing run may write**; `mark_corrections` is append-only (no update, no delete, no soft-delete column). `results` = one row per (exam, candidate) with `gpa`, `gpa_without_optional`, both merit positions and its **own** `grading_snapshot`. `result_publications` are **versioned** with at most one active (partial unique `WHERE is_active`) — portal and public visibility read the ACTIVE publication, never `exams.status`, because the status machine cannot rewind past PUBLISHED. `result_runs` hold durable processing progress. `combined_results` mirror `results` for a weighted merge, `uq(session_id, name, enrollment_id)`, with the weight set frozen per row. **Live since M16:** `fee_heads` (per-school chargeable items, refundable flag) →1:N→ `fee_structures` = the class × head price for a session (identity unique NULL-safe over the optional group). `student_fee_overrides` = a per-enrollment concession (percent capped 0–100 by CHECK). `invoices` key on **`enrollment_id`**, one monthly bill per candidate per month (`uq_invoices_enrollment_month` — ad-hoc invoices carry no `billing_month` and so never collide), with `payable = subtotal − discount + fine` pinned by `chk_invoices_payable` (the fine job moves `payable` in step, or the CHECK refuses the write) and status **derived**, never assigned (`payable ≤ 0 ⇒ PAID`, so a waived invoice is never late-fined) →1:N→ `invoice_items`. `payments` →1:N→ `payment_refunds`; a `SUCCESS` payment must carry `paid_at`, and an online one must also carry `verified_at` (`chk_payments_success_evidence`) — a forged gateway callback cannot credit money. **Live since M17:** `notification_templates` (per `(code, channel, language)`, live-unique) render into `notifications` — the **append-only** delivery log *and* the in-app inbox (an IN_APP row with a NULL `read_at` is an unread badge; a `SENT`/`DELIVERED` row must carry `sent_at`, a `FAILED` one an `error`; a `dedupe_key` partial-unique collapses a repeat within a window). `notices` (audience + scheduled `publish_at` + website-visibility) feed the board; `sms_credits` is the **append-only** running-balance ledger the dispatcher decrements per SMS part (`balance_after` pinned ≥ 0). **Live since M19:** nine website tables sharing ONE publication enum (`web_content_status_enum`), so "only PUBLISHED is public" needs no per-table exception: `cms_pages` and `news_posts` (slug unique per school among live rows via a partial unique; a PUBLISHED row must carry `published_at` by CHECK, because it is both the feed sort key and the RSS `<pubDate>`), `galleries` →1:N→ `gallery_items` (**hard-deleted** — an album's items are replaced as a set, the M13 `timetable_entries`/M14 `seat_plan_entries` precedent), `downloads` (`download_count` is the one column an anonymous visitor may move, and only upward), `careers` →1:N→ `career_applications`, `faqs`, `committee_members`, and `contact_messages` (a REPLIED row must carry `replied_at` and anything past NEW a `read_at` — the M16/M17 evidence rule; a CHECK also refuses a message with neither phone nor email). **Live since M20:** `accounts` is a tree per school inside five fixed groups (`account_group_enum`), where `is_group` marks a **heading** — a subtotal that holds no money, pinned by `chk_accounts_group_node_empty`, because only leaves may be posted to; `is_system` marks the five accounts auto-posting resolves to, which may be renamed but never deleted or deactivated. `vouchers` →1:N→ `voucher_entries` (**hard-deleted** with their voucher and replaced as a set while DRAFT — the M13/M14/M19 wholesale-replacement precedent), each line one-sided and non-negative by `chk_voucher_entries_one_sided`; that Σdebit = Σcredit *across* a voucher is deliberately **not** a trigger (a CHECK cannot see siblings) and lives in `voucher.engine.ts`. A POSTED voucher is immutable: `cancel()` marks it CANCELLED and writes a mirror-image reversal linked by `reversal_of_voucher_id`, and **both stay in the ledger** — reports read `posted_at IS NOT NULL`, not `status = 'POSTED'`. `vouchers.source_ref` is the auto-posting idempotency key (partial unique excluding CANCELLED), and `chk_vouchers_source_ref_shape` makes a MANUAL voucher never carry one. `posting_maps` (kind × ref_key → account, append-only kinds), `budgets` (session × account × optional month, COALESCE identity index) and `fiscal_periods` (non-overlapping, CLOSED locks everything dated inside). **Live since M21:** `leave_types` is a TABLE (it **replaced** `leave_type_enum`, because a taxonomy carrying an annual quota, a carry-forward cap and a paid/unpaid flag is data) →1:N→ `leave_balances` (one row per person × type × session, `uq_leave_balances_identity`, `used` moved only by the approval flow) and `leave_applications` — the polymorphic successor to M08's `teacher_leaves`, which the M21 migration **copied across and dropped**. An application stores its `days` rather than deriving them, because the working-day calendar it was counted against can be edited afterwards and an approved leave must not start consuming a different amount of quota. `salary_structures` →1:N→ `salary_components` (**hard-deleted** and replaced as a set — the M13/M19/M20 wholesale-replacement precedent). `employee_salaries` is **history**: a change writes a NEW row with an `effective_from`, and `uq_employee_salaries_identity` keeps exactly one row per person per date so "the salary in force on 1 March" has one answer. `payroll_runs` (one live run per month, the partial unique excluding CANCELLED so a cancelled run frees the month — the M11 rule; `month` pinned to the 1st by CHECK, or the unique would compare something other than what it claims) →1:N→ `payslips`, every figure **stored** rather than recomputed (the M14/M15 snapshot rule) with a `breakdown` JSON that carries the engine's input snapshot, so an edit-with-reason recomputes exactly, months later, through the same engine. `bonus_runs` are rules resolved per person at generation. `pf_ledger` is **append-only** with a running `balance_after` (the M17 `sms_credits` pattern), one CONTRIBUTION row per payslip behind a partial unique. `teachers` and `staff_profiles` gained `exit_date`, because M07/M08 recorded a status *change* but never its date and payroll cannot prorate a leaver's final month without one. **Live since M22:** `assignments` = one piece of work for a (session, section, subject) set by a teacher, walking `DRAFT → PUBLISHED → CLOSED` with `published_at`/`closed_at` as the evidence (`chk_assignments_status_evidence`) and `due_at > assigned_at` pinned by CHECK; both timestamps are wall-clock **instants** rather than dates, because "due Thursday" at a BD school means a time of day and 23:59 vs 00:01 is exactly what `is_late` decides. `due_reminder_sent_at`/`no_submission_alert_at` are the two jobs' idempotency (the M12 `absent_notified_at` column-as-dedupe pattern). →1:N→ `assignment_submissions`, keyed on **`enrollment_id`** like every other academic record and carrying **no soft delete** — a resubmission replaces the row in place so the evaluation hanging off its id stays attached (the M15 `marks` rule), which is also what lets `uq_assignment_submissions_identity` be a PLAIN unique rather than a partial one; `chk_assignment_submissions_content` refuses a row with neither text nor a file, because an empty "submission" would land on the teacher's grid as handed-in and inflate the one percentage this module exists to report. `is_late` is **stored**, not derived (see §16). `learning_materials` hang off a class with an **optional** section, where NULL means class-wide — which is why `class_id` is stored alongside rather than read through the section, why the visibility query writes the NULL branch out explicitly, and why that FK is `ON DELETE RESTRICT` rather than Prisma's default SET NULL for an optional relation (a deleted section would otherwise silently promote a private material to the whole class). `chk_learning_materials_link_scheme` pins `link_url` to `https://…` at the database, because that column is rendered as an anchor in a student's browser. **Live since M23:** the library separates the **title** from the **copy**, and everything follows — `books` (bibliographic; `isbn` nullable and deliberately NOT unique, because a BD school’s shelves carry unISBN’d local guides, duplicate donations and reprints that never changed their number — a checksum is validated on write instead) over `book_categories`/`authors`/`publishers`, with `book_authors` **hard-deleted and replaced as a set** (the M13/M19/M20 precedent). `book_copies` is the physical volume, and `uq_book_copies_accession` **ignores `deleted_at`**: an accession number is a barcode label stuck inside a book and is never reused, exactly as an employee ID (M07) or a student UID (M09) is never reused; `uq_library_members_card` is the same rule for a printed card. `library_members` is polymorphic over `students`/`teachers`/`staff_profiles` with no FK (the M12 `staff_attendances` / M21 `leave_applications` precedent), and `max_books` is **stored on the card** rather than read from settings at issue time, so an exception granted to one student survives a later edit of the school-wide default. `book_issues` carries **no soft delete** — a loan is history and a wrongly-issued copy is returned, not erased — which is what lets **`uq_book_issues_open_copy` (`WHERE returned_at IS NULL`)** make “one physical book, one pair of hands” true no matter what a service forgets. Its money columns are the module’s ledger: `fine_amount` assessed, `fine_collected` + `fine_waived` the two ways it goes away, and **`fine_paid` DERIVED by `chk_book_issues_fine_paid`** rather than assigned (the M16 `deriveStatus` rule pinned at the database — the one invariant a “mark as paid” button could otherwise break); `chk_book_issues_waiver_evidence` refuses a write-off with no name and no reason on it, and `overdue_days`/`holiday_days` are **stored** so editing the calendar later cannot make a settled fine disagree with the receipt already handed over. `book_reservations` is a queue on a **title** — `reserved_at` IS the rank, so a cancellation never rewrites anybody’s position — and the copy status is its shadow (a copy is RESERVED exactly while a READY hold points at it, `uq_book_reservations_held_copy`). `stock_verifications` →1:N→ `stock_verification_scans` (hard-deleted with the parent) hold a physical count whose **expected set is resolved at CLOSE, not at open** (a book issued mid-count is legitimately absent) and whose diff is then **frozen into the row** (the M14/M15 snapshot rule). **Live since M25:** `vehicles` (the three expiry dates are the module's most load-bearing columns — an unfit or uninsured bus full of children is the thing it exists to stop happening quietly — and `uq_vehicles_reg_no` is unique among **live** rows, the OPPOSITE of the M07/M09/M23 never-reuse rule, because a plate is issued by the BRTA and belongs to the vehicle rather than to the school's numbering) and `drivers` (`staff_id` optional — a BD school's driver is as often the contractor's as the payroll's — with a live-rows unique on the licence and one driver row per employee). `routes` carry a vehicle, a driver, an optional **substitute** (roadmap §8's temporary replacement, a field rather than a rota) and a helper; `chk_routes_shape` refuses driver = substitute, because the substitute exists *because* the driver is away. `route_stops` are **soft-deleted** (an assignment points at one, and a deleted stop must still be able to say what a rider was paying) and carry **the monthly fare** — distance is what a BD school charges for, so the fee is on the stop and never on the route; `uq_route_stops_order` makes the sequence real, which is why reordering is a two-pass write (the M11 renumber problem). `transport_assignments` key on **`enrollment_id`** and are a service **window**: `effectiveFrom = resumed_at ?? start_date`, `effectiveTo = end_date ?? suspended_at ?? open`, pinned by `chk_transport_assignments_window` and `chk_transport_assignments_status_evidence` (ENDED carries an end date, SUSPENDED a suspension date, and an ACTIVE row may **not** still carry one) — the M21 `exit_date` reasoning, because a status change with no date cannot answer "how much of March does this rider owe". `uq_transport_assignments_live` excludes only ENDED, so a **suspended rider still holds their seat**. The stop is pinned to its route by a **composite foreign key** `(route_id, stop_id) → route_stops(route_id, id)` — a single-column FK would accept a stop from another route, and the school would find out when the driver's sheet printed a child waiting at a corner the bus never passes. `vehicle_expenses` carry a nullable `odometer` (a toll receipt has no reading) and `chk_vehicle_expenses_shape` requires `amount > 0`. **Live since M24:** the store separates the **counted** from the **identified**, and every other decision follows — `items` carries a type, a base unit and an optional `pack_size` (§8's `box_size`, generalized: a ream is 500 sheets and a box is 12 pens, one column rather than one per packaging word) but **no quantity column at all**, because a stored balance is a second source of truth that drifts from the movements beneath it. That balance lives in **`stock_ledger`**, which is append-only like `audit_logs`/`sms_credits`/`pf_ledger` (no `deleted_at`, no `updated_at`, no UPDATE path) and carries a **running** `balance_after` written under `SELECT … FOR UPDATE` on the *item* row; `chk_stock_ledger_one_sided` makes each row a movement in exactly one direction (the M20 `chk_voucher_entries_one_sided` shape) and pins `balance_after >= 0`, which is the invariant the whole module protects — a school cannot issue what it does not have, and the database says so when a service forgets. `chk_stock_ledger_reason` demands a reason on an ADJUST or a DISPOSE, because those are the movements a stock-take dispute turns on. `purchases` are gap-free (`PO-{YY}-{SEQ5}`) and **immutable once RECEIVED** — the correction is a cancellation writing reversing entries, the M20 voucher rule in a second ledger — and `purchase_items` are hard-deleted and replaced as a set while DRAFT (the M13/M19/M20/M21 precedent) storing the quantity **twice on purpose**: `qty` as the clerk typed it against the invoice, a *snapshot* of `pack_size`, and `base_qty` pinned by `chk_purchase_items_shape` to `qty × pack_size`, so the ledger only ever speaks base units and the two can never drift. `asset_units` is one physical thing with a tag, generated one row per unit at RECEIVE; **`uq_asset_units_tag` ignores `deleted_at`** (the M07 employee-ID / M09 student-UID / M23 accession rule — it is a sticker on a projector) while **`uq_items_code` is scoped to LIVE rows** (the M25 plate rule — it is a catalogue label the school chooses), and the two sitting one table apart is the clearest statement of that distinction the schema has. `stock_issues` →1:N→ `stock_issue_items` are child rows rather than §3's offered JSONB, because a return has to move a quantity on ONE line of a multi-item slip; `chk_stock_issue_items_returned` caps a return at what went out (§6) and the slip's status is **derived** by `deriveIssueStatus`, never assigned. **One holder shape** — `(kind, department | person | room)` — answers "who has it" for both the issue recipient (`chk_stock_issues_recipient`) and the asset custodian (`chk_asset_units_custodian`, whose all-NULL branch is a unit sitting in the store held by nobody); the person half is polymorphic over `teachers`/`staff_profiles` with no FK (the M12/M21/M23 precedent), and DEPARTMENT exists because §8's shared lab equipment belongs to the science department and to no one person. **Live since M26:** the boarding house separates the **building** from the **bed**, and the rest follows — `hostels` carry a `type` (BOYS/GIRLS, deliberately with no `MIXED`: the gender check the module exists to enforce has no meaning without it) and a *declared* `capacity` kept **beside** the real bed count rather than instead of it, because a warden who has quietly added a fourth bed to a three-bed room is exactly what the head needs to see. `hostel_rooms` carry the **seat rent** (an AC double and a six-bed shared room are not the same product — M25's fare-on-the-stop reasoning applied to a room) and a `bed_count` that is *intent* against `hostel_beds` rows that are *fact*; the mismatch is reported, never silently repaired, because deleting a bed somebody is asleep in is not something a form field should do. **`hostel_id` is denormalized down the whole chain and pinned at every step by a COMPOSITE foreign key** — `hostel_beds(hostel_id, room_id)`, `hostel_allocations(hostel_id, bed_id)`, and **both** of `mess_enrollments`' FKs — the M25 `(route_id, stop_id)` technique, four times; the one that pays for the scheme is `(hostel_id, plan_id)`, because a boarder eating on another building's plan produces an invoice that still balances and is simply the wrong number. `hostel_allocations` key on **`enrollment_id`** and are a residency **window**: `[resumed_at ?? start_date, end_date ?? suspended_at ?? ∞)`, pinned by `chk_hostel_allocations_window` and `chk_hostel_allocations_status_evidence` (VACATED carries an end date, SUSPENDED a suspension date, and an ACTIVE row may **not** still carry one) — the M21 `exit_date` / M25 service-window reasoning, third time. `uq_hostel_allocations_live_bed` and `uq_hostel_allocations_live_enrollment` both exclude only VACATED, so a **suspended boarder still holds their bed**, and the first of those is what makes `hostel_beds.status` safe to treat as a **shadow**: the index is the truth, the column is written in the same transaction so the occupancy grid can be drawn from one table, and `MAINTENANCE` is the one value that is genuinely the bed's own fact. The deposit is the only money in the module the school does not earn, and `chk_hostel_allocations_deposit` says so three ways — never more back than was taken, never a refund with no amount or date behind it (the M16/M17 evidence rule), and never a refund to somebody still living there. `mess_plans` hang off a hostel; `mess_enrollments` are a window with a live-rows partial unique so a boarder moving from full board to lunch-only mid-year is billed correctly for both halves. `meal_offs` carry **`credit_month`**, pinned to the 1st by CHECK and decided **once, at approval** (the month after the later of the last day away and the decision) — because the obvious alternative, a "credited" flag the invoice run consumes, would be eaten by an invoice **preview** that raises no bill. **Live since M27:** a certificate is the one record in the system that keys on **`student_id`** rather than `enrollment_id` — the deliberate exception to the spine, because a certificate is about a person and their whole time at the school; `enrollment_id` and `session_id` sit beside it as *where the snapshot was taken from*. `certificates` freeze **both** `data_snapshot` (everything the page prints) and `body_html` (the layout it was rendered through) at issue, so re-printing years later reproduces the page after the template was redesigned and the name corrected — the M14/M15 grading-snapshot and M21 payslip-breakdown rule, applied to the only artifact that leaves the building on letterhead. `uq_certificates_no` and `uq_certificates_verify_code` both **ignore `deleted_at`** (the M07/M09/M23/M24 never-reuse rule, in its strongest case: the number is on a document a university may quote back in ten years), and the verify code is scoped **globally** rather than per school because the public endpoint is reached without one. `chk_certificates_status_evidence` makes a status carry its own evidence — an ISSUED row has a number, a code, a date and a non-empty snapshot; a DRAFT has none of the first three, so it can never be one URL away from reading VALID. `chk_certificates_issue_kind` pins `(kind = ORIGINAL) = (original_certificate_id IS NULL)` over a self-FK, which is roadmap §8's re-issue chain made structural: a DUPLICATE reprints a certificate that is still valid, a CORRECTION replaces one that is not, and the two have **opposite** preconditions. `certificate_templates` are living rows; `archive_folders` is a self-referencing tree whose identity index COALESCEs the nullable parent (the M06 trick) and `archive_files` carries a real `TEXT[]` of tags behind a GIN index with an optional FK-less `(linked_type, linked_id)` pair pinned by CHECK to be wholly set or wholly absent. **Live since M28:** `tickets` is where the module's promise is kept — **`chk_tickets_raiser` refuses an ANONYMOUS row that carries a raiser id, a contact block OR an ip**, which is the strongest statement in the schema that a promise made on a form is enforced somewhere a service cannot forget it; its mirror refuses a PUBLIC row with no contact (a complaint the school can never reply to) and a GUARDIAN/STUDENT/STAFF row naming nobody. `chk_tickets_status_evidence` makes a status carry its evidence (RESOLVED and CLOSED both need a resolution and a time; CLOSED stamps `closed_at`, which is the origin the seven-day reopen window is measured from and without which "within 7 days" cannot be evaluated at all), and it permits a **satisfaction rating on a REOPENED row** — that state means there *was* a resolution and it did not hold, and excluding it would force a reopen to destroy the score the family gave the first attempt. `uq_tickets_no` **ignores `deleted_at`** (the M07/M09/M23/M24/M27 never-reuse rule: the office told a parent to quote it). `is_sensitive` is **stored at creation** from the category rather than derived on read, so narrowing the sensitive list later cannot expose complaints already filed under it. `ticket_comments` is **append-only** — no `updated_at`, no `deleted_at`, no update path (the M03/M17/M20/M24 precedent, and exactly roadmap §3's column list) — and `is_internal` is the whole reason it exists, the office needing somewhere to think before it replies. `visitors` has **no status column**: `check_out IS NULL` IS the in-building list, so nothing can fall out of step with it (the M26 bed-status lesson, inverted — where an index can be the truth, a column should not try), and `auto_checked_out` is pinned by CHECK to a row that actually has a check-out, because the flag means "a machine wrote this time" and one with no time behind it says nothing. `gate_pass_no` is unique ignoring `deleted_at` (a card in somebody's hand inside a building full of children); the host is the M12/M21/M23/M24 polymorphic pair over `teachers`/`staff_profiles` with no FK, wholly set or wholly absent. `appointments` are deliberately **not** visitor rows — an approved appointment nobody kept is a NO_SHOW the register must keep, and creating the visit at approval would put somebody in the building who never came. `alumni.student_id` is **optional and does not identify the row** (a school that opened in 1978 has forty years of alumni who were never in this system), and when it is set **`uq_alumni_student` — partial on APPROVED, live rows — is roadmap §8's conflict queue with no queue table**: a second claimant may register and sits PENDING, and the index is what stops two people being approved as the same person. `is_public_profile` defaults **false**, because publishing a directory entry is a second decision from making one. `alumni_events.fee` NULL is a free event and `0.00` is one priced at nothing — the accounts read them differently. `donations` are the **fifth immutable ledger**: `uq_donations_receipt` ignores `deleted_at`, there is no update path, and `chk_donations_shape` pins amount > 0 and makes a cancellation carry both a date and a reason or neither. Full graph grows per module; see each module §3.

## 9. Authentication Flow

**Live since M02.** Login (email/phone + password, argon2id) → access JWT 15 min (in memory) + rotating opaque refresh 7/30 d (httpOnly `hs_refresh` cookie, path `/api/v1/auth`) → rotation with reuse-detection (reuse outside 5 s two-tab grace ⇒ revoke ALL sessions + SMS alert; rotation never extends the session window). **Since M09** one contact may back one account PER user type (a guardian who is also staff) — uniqueness is `(school_id, user_type, contact)`, and login verifies the password against EVERY candidate for the identifier (`UsersRepository.findAllByIdentifier`), a failed attempt counting against each unlocked one; OTP/reset target the oldest candidate until username login lands. OTP (6-digit, hashed, 5 min, 3 attempts, 60 s resend) for reset/verification; verify-otp mints a 10-min reset token. Lockout 5 fails/15 min (423). Generic errors everywhere (no account enumeration). Frontend: axios single-flight refresh interceptor → `/auth/refresh`; `proxy.ts` guards route groups via the `hs_session` hint cookie; forced-change interstitial when `must_change_password`. Bootstrap Super Admin comes from the seed (`admin@hexschool.local`).

## 10. Authorization Flow

**Live since M03.** RBAC: permission codes registry (TS code = source of truth, idempotently synced to `permissions`; removed codes orphan-flagged and denied) → roles (11 system roles seeded per school, non-deletable/non-renamable, core sets locked extend-only) → users (`user_roles`; every user keeps ≥1 role, last `super-admin` holder protected). `PermissionsGuard` + `@RequirePermissions()` (AND) / `@RequireAnyPermission()` (OR); permissions cached in Redis 5 min (`perm:{userId}`), invalidated on role change, DB fallback if Redis is down; Super Admin (`user_type`) bypasses. **Guard chain is pinned in `AppModule` providers (Throttler → JwtAuthGuard → PermissionsGuard) — global-guard order follows provider registration order, so never register APP_GUARDs from feature modules.** Role edits use optimistic concurrency (`expectedUpdatedAt` → 409). Frontend `<Can>`/`usePermissions()` + `ADMIN_MENU` permission-per-item config (UI gating only; API is authoritative). **Portals (M18) are authorized by OWNERSHIP, not permission codes** — the `OwnershipGuard` + `PortalResolverService` resolve the logged-in user to the student ids they own (student=self, parent=children via `student_guardians`, teacher=what they teach); `assertOwnsStudent` is the single IDOR chokepoint (a `@OwnsStudent('childId')` route 403s any other id, re-verified in the services). The admin/accountant dashboards ARE permission-gated (`dashboard.admin`/`dashboard.accountant`); the reports hub self-filters by permission.

**Audit (M03):** every successful mutating request writes an immutable `audit_logs` row via the global `AuditInterceptor`. New modules: set precise diffs from services via `AuditContextService.set({entityType, entityId, oldValues, newValues})`; use `@Audit({action})` for verb overrides and `@SkipAudit()` only for machine noise. `action` is VARCHAR — extend `AUDIT_ACTIONS` (both repos) instead of migrating an enum.

## 11. Global Business Rules

- One `is_current` academic session (DB partial unique index since M05); sessions never overlap in dates; COMPLETED sessions are read-only for entry flows — **enforced since M12** (attendance marking refuses a COMPLETED/ARCHIVED session; M15 marks entry must do the same). Activate rolls the demoted ACTIVE session to COMPLETED.
- One enrollment per student per session; roll unique per section.
- One attendance record per student per date (**per period since M13** — `period_id` has its FK and `attendance.mode = 'period'` turns it on; a `periodId` sent while the mode is `daily` is refused, not ignored); attendance may not be taken for a future date, outside its session, or on a holiday without `attendance.holiday.override`. Attendance % = `(present + late + ½ half-day) ÷ working days`, working days excluding holidays, weekly off-days and days before the student's `enrollment_date`.
- **Only PUBLISHED routines are portal-visible** (M13). One DRAFT + one PUBLISHED per section per session; publishing archives the version it replaces, so `effective_from` + `version` reconstruct any past date's routine. Drafts are deletable; published/archived versions are history.
- Published results/receipts/vouchers/certificates are immutable — corrections via reversal/reissue with audit trail. **Enforced since M15:** a LOCKED mark changes only through the correction flow (reason mandatory, `mark_corrections` written first), and a re-issue is publication version N+1 with a changelog note, never an edit of the live one.
- **Result visibility is the ACTIVE publication row, not `exams.status`** (M15). Unpublishing revokes the active version and hides the results everywhere without touching the computed numbers.
- **NCTB result rules** (M15): GPA is the mean of *grade points* over compulsory subjects; the optional (4th) subject adds only the points **above** `exam.optional_bonus_base` and never joins the divisor; one compulsory F is a fail with GPA 0.00; an optional F never fails anybody; a missed per-component pass threshold forces the failing grade regardless of the total. Merit is competition ranking (1, 2, 2, 4) among PASSED candidates only.
- A grade is a property of the **run**, not of the mark: `marks.grade`/`grade_point` are written only by a processing run, and re-entering or correcting a mark clears them.
- All money NUMERIC(12,2) BDT; every monetary override needs permission + reason.
- **Fees (M16):** an invoice's status is **derived, never assigned** (`fine.engine.ts` `deriveStatus`; `payable ≤ 0 ⇒ PAID`, so a fully-waived invoice is never late-fined); the monthly batch is idempotent per `(enrollment, month)`; a payment allocates **oldest-due-date-first**; a late fine is charged **at most once per calendar month**; a refund is refused against a non-refundable head and never exceeds what was paid; overpayment needs `fee.overpay`. **Online money is SUCCESS only after a server-side `verify()` whose amount matches ours** — a gateway callback is a hint, never a verdict — and a SUCCESS online payment must carry `verified_at` (`chk_payments_success_evidence`). Dues are read via `LedgerService.outstandingFor`, the single dues source for every gate (`EXAM_DUES_GATE` live).
- **Communication (M17):** every module-originated message goes through `NotificationService.send()` — no direct gateway calls. A message is rendered from a template (per code/channel/EN-BN, variables validated against a per-code allow-list), held out of **quiet hours** unless EMERGENCY, **deduped** on `(destination, template)` within a window (a DB partial unique; two absent siblings merge into one SMS), and **credit-accounted** per SMS part (a metered school's send is refused when it cannot cover the parts). SMS is real via a configurable BD-gateway adapter with a log-only fallback; the worker records SENT→DELIVERED/FAILED and a DLR webhook (secret-verified) closes the loop.
- **Portals (M18):** a portal user sees only what they OWN (student=self, parent=children via `student_guardians`, teacher=what they teach) and only PUBLISHED artifacts (published routine, active result publication, published notices) — enforced by ownership, not a permission code. Dashboards are cached best-effort in Redis and render zero-states for an empty school. Result-withhold-on-dues, portal Pay-Now and the dues-reminder blast are live here.
- **Website (M19):** only `PUBLISHED` content — and, for notices, `is_website_visible` — is served publicly; the filter lives in the repository's `published*` helpers so an endpoint cannot forget it. A draft is reachable only through a **signed token naming that exact row**, and a missing page, an unauthorised draft, a withheld student and a switched-off feature all return the **same** 404 — a public endpoint never confirms that something exists. Author markup is **sanitized on write** against an allow-list, so the stored row is the guarantee. `published_at` is derived, never assigned: first publish stamps it, re-publish and unpublish preserve it. Public writes (contact, career application, verification) carry reCAPTCHA + a route throttle, and the contact form adds a per-IP hourly cap.
- **Accounting (M20):** every POSTED voucher balances **exactly** (Σdebit = Σcredit to the paisa) and only **leaf** accounts may be posted to — a heading is a subtotal and would double-count. A POSTED voucher is **immutable**: the correction is `cancel()`, which writes a mirror-image reversal dated *today* (back-dating it would restate a month already signed off) and leaves both documents in the ledger — so the ledger predicate is **"every voucher that was ever posted"** (`posted_at IS NOT NULL`), never `status = 'POSTED'`. An **auto-posted voucher may never be hand-edited** — it is the machine's record of a real payment. Fee money posts itself on `payment.success` (Dr cash/bank/clearing, Cr fee income split per head by largest remainder so the two sides match exactly) and reverses on `payment.refunded`, idempotent on `source_ref`. **No posting into a CLOSED period** — except a backdated payment, which posts into the next open one *with a note* (roadmap §8, BD practice, `accounting.backdate_after_close`); closing refuses over a DRAFT dated inside the range; reopening needs `accounting.period.reopen` and a reason. Cash may not go negative (`HARD`/`SOFT`/`OFF`), and a voucher may not be dated further ahead than `accounting.future_voucher_days` (default 0). The Accountant keeps the books but holds neither `voucher.cancel` nor `accounting.period.reopen` — the M16 separation-of-duties rule.
- **HR & Payroll (M21):** leave costs **working days**, not calendar days, and consumes a **per-session** balance — approving decrements `used` inside the same transaction as the status flip, and withdrawing an APPROVED leave hands the days back (which is what `CANCELLED` is for: a person who withdraws is not a school that refused). An **UNPAID** leave type is never "over quota" — the days come out of pay, not an entitlement. A salary assignment is **history**: a change writes a new row from a date, never an edit, so regenerating March reads March's salary. **One live payroll run per month**; regeneration wipes and rewrites while DRAFT/GENERATED; an **APPROVED run is frozen** and corrections go on next month's run as an adjustment line (the M15/M20 immutability rule); a **DISBURSED** run cannot be cancelled. **HELD payslips** are excluded from the disbursement, the bank advice and the voucher until released. A day covered by approved leave is **never also an absence**, and an **unmarked** working day is treated as present — recording an absence is the register's job (the M15 "a missing mark is never a zero" rule). The provident fund follows the **pay scale**, not the attendance register. Net pay is non-negative **by construction** (the discretionary deductions absorb the remainder) rather than by a floor, so the payslip's lines keep adding up to its total and the salary voucher keeps balancing.
- **Assignments (M22):** a teacher may set, read and mark work only for the section-subjects they hold **right now** — the policy re-reads `teacher_section_subjects` at every request, so a reassignment moves the rights with it; `assignment.all` widens that to the school, and the original author keeps access to work they already marked. **Only PUBLISHED work is visible to a section**, and a draft read from the portal returns the same 404 a non-existent id gets (the M15/M19 rule that a read must not confirm what the caller may not see). A student submits only for **their own enrollment**, only to their own section, only late if `allow_late`, and **a parent may never submit** — reading their child's list is the whole of the parent's role here. A resubmission **replaces the row and clears the mark, feedback and evaluator**, because whatever was said about the old work no longer describes what is on file (the M15 "re-entry clears the grade" rule); an EVALUATED submission can only be reopened by the teacher's `return`, which requires feedback and clears the mark. Marks may not exceed `full_marks`, and `full_marks` may not be lowered below a mark already given. **CLOSED locks evaluation**, and the unlock is a separate code (`assignment.evaluate.override`) the Teacher baseline deliberately lacks. Deleting an assignment is refused once anybody has submitted — the FK cascades, so the school's route is to close it, not to erase what a class handed in (the M14/M15 "blocked once marks exist" guard). `is_late` is stored, never recomputed. Author HTML is sanitized on **write** through the M19 allow-list sanitizer.
- **Library (M23):** a copy must be AVAILABLE — or held **for this member** — to be issued, and ISSUED/LOST/DAMAGED/WITHDRAWN are **structural** refusals no permission reaches (the M13/M14 two-tier override split); over-limit, unpaid-fine, overdue-holding, suspended and duplicate-title are **policy** refusals `library.issue.override` may push past, recorded against a name. The unpaid-fine total spans **every** loan, returned or not — otherwise a habitual defaulter clears the block by handing everything back. All of those verdicts come from **one** `canIssue` call, so the greyed button, the 409 and the OPAC’s blocked reason cannot disagree. A **renewal is refused while the loan is overdue**, because renewing moves `due_at` and would erase a fine already earned; the new period runs from *today*. Overdue = chargeable days × rate, capped, with grace off the lateness and holidays off the chargeable days **in that order**. A lost or damaged copy is charged at price × multiplier, falling back to `library.default_book_price` (charging nothing for an unpriced book is how the unpriced half of a catalogue becomes the half that goes missing), and writing off a copy that is on loan **closes that loan** so the member’s slot is freed. `fine_paid` is derived; a collection may not exceed what is outstanding; a waiver carries a name and a reason. A returned copy somebody is waiting for is **held, not shelved**. Only AVAILABLE/RESERVED copies are expected at a stock-take, and the expectation is resolved at close. **The Librarian takes money and may not write it off** — `library.fine.collect` and `library.fine.waive` are different codes held by different people (the M16/M20/M21 rule).
- **Transport (M25):** a rider's assignment is a service **window**, not a status — suspending, resuming and ending each write a **date**, and M16 bills `[resumed_at ?? start_date, end_date ?? suspended_at ?? ∞)` intersected with the month. The transport line arrives at invoicing **already prorated** and must be added with `prorated: false`; proration by enrollment date and proration by service window answer different questions, and multiplying them bills a mid-month joiner (21/31)² of the fare. The fare lives on the **stop**, so a stop with riders on it may not be deleted (that would stop those families being billed silently) and a route split matches stops **by name** to preserve what a family pays. Over capacity **warns**; `transport.capacity_hard_block` makes it a policy refusal and `transport.assign.override` is what passes it — there is no structural seat rule, because a 40-seat bus carrying 41 children is a real thing and a system that made it unrecordable would be lied to. A **SUSPENDED rider still holds their seat**; only ENDED frees it. A route needs ACTIVE status and a vehicle before children go on it, but a vehicle in **MAINTENANCE passes** (the bus is back on Monday). A lapsed document is a **warning, never a refusal**, and a *missing* expiry date is not a valid one — it reports UNKNOWN and appears in the alert list. Vehicle spending posts to the ledger as a **DEBIT** voucher (the first auto-posted one that spends rather than receives), and a posted expense is not editable in place; deleting it leaves the voucher standing, because reversing a posted entry is the accountant's call (M20).
- **Inventory (M24):** a **CONSUMABLE is counted and an ASSET is identified** — the first is a ledger balance, the second is tagged rows, and an asset can never be issued by quantity (structural; no permission reaches it). **The stock ledger is the source of truth and a balance is never edited directly** (roadmap §6): there is no quantity column on an item, `balance_after` is a running total written under a row lock, every movement is one-sided, and `balance_after >= 0` is a CHECK rather than a service rule. An adjustment is expressed as the **movement it implies**, not as a new balance — a count that finds 8 where the ledger says 12 writes `qty_out: 4`, and the remark records what it was corrected *from*. Quantities are whole except for LITER and KG (§7) and never carry more than three decimals; the pack→base conversion is a stored fact pinned by CHECK, not a multiplication anybody repeats. A **RECEIVED purchase is immutable** and cancelling it writes reversing entries, which means a school that has already issued the stock genuinely cannot un-receive it — and that refusal is the point. A **written-off unit never comes back**: there is no transition out of DISPOSED or LOST, because the disposal was an approved act with a name on it, and a unit that turns up later is registered anew with its own tag. DISPOSED/LOST are excluded from register counts and kept in a separate written-off list, because "what happened to the projector" is the question an audit actually asks. An **asset tag is never reused** (it is printed on an object) while an **item code is** (it is a label the school chooses). Stock is valued at **last price × qty** and the report prints that method on its face; consumables are **expensed at purchase**, so the stock ledger and the ledger of accounts deliberately disagree about unissued stock. **The Office Staff runs the store and holds none of the three codes that take property OFF the books** — cancel a received delivery, correct a count, write an asset off (the M16/M20/M21/M23/M25 rule, continued into the store room).
- **Hostel (M26):** a hostel is **BOYS or GIRLS**, and a student whose gender does not match is a **structural** refusal no permission reaches; a student recorded `OTHER` matches neither and is a **policy** refusal `hostel.allocate.override` may pass, because refusing to house that child is the school's decision and not the system's. A residency is a **window**, not a status — suspending, resuming and vacating each write a **date**, and M16 bills `[resumed_at ?? start_date, end_date ?? suspended_at ?? ∞)` intersected with the month. The two hostel lines arrive at invoicing **already prorated** and must be added with `prorated: false` (the M25 rule; the seat rent and the mess charge are separate heads because they move independently and a parent asks about one or the other). Roadmap §8's precedence is absolute: **the allocation window first, then everything inside it** — a mess enrolment nobody closed is bounded by the vacate date, and meal-off days are credited only where they overlap the residency, because a boarder cannot be refunded for a day they were never billed for. A **SUSPENDED boarder still holds their bed**; only VACATED frees it, and `hostel_beds.status` is a **shadow** of that partial unique rather than the truth (only the allocation flow writes it; a form may not hand-set OCCUPIED or VACANT). A room may not be taken out of service, and a building may not change what it is *for*, while anybody lives in it — the refusal names how many people have to move, which **is** roadmap §8's transfer wizard. A transfer keeps the residency dates (restarting would re-bill the month) and may not cross buildings. Vacating reads dues through **`LedgerService.outstandingFor`** — the single dues source every gate uses — warns by default and refuses only when `hostel.vacate_block_dues` is on, which `hostel.vacate.override` then passes. The **security deposit is money the school HOLDS**: it posts as a matched voucher pair (Dr cash / Cr `2140` at allocation, the mirror at refund), never touches the income statement, is never refunded for more than was taken or to somebody still living there, and every deduction carries a reason. A meal-off must meet `hostel.meal_off_min_days` and may not overlap a live request; its **credit month is decided once, at approval**, so regenerating a month gives the same number and an invoice PREVIEW cannot consume the credit. The credit is capped at the month's mess charge, and the invoice total is floored at zero. **The Office Staff runs the hostel and may neither hand a deposit back nor override the dues gate** — those are the accountant's and the head's (the M16/M20/M21/M23/M24/M25 rule).
- **Certificates (M27):** an issued certificate is a **physical object in somebody else's possession**, so nothing edits one — `data_snapshot` and `body_html` are frozen at issue, a wrong name is a **revoke plus a CORRECTION**, a lost original is a **DUPLICATE**, and both stay in the register, linked (the M15 re-issue / M20 reversal rule, in a third ledger). Numbers are sequential **per type, per year, and never reused**, claimed inside the issuing transaction. **Only ISSUED certificates verify VALID**; a DRAFT gives the same NOT_FOUND an unknown code gets, while a REVOKED one deliberately reports REVOKED *with the school's reason*, because a cancelled document and a forgery must not look identical to whoever is checking. **A DUPLICATE needs a still-valid original and a CORRECTION needs a revoked one** — opposite preconditions, or two documents would verify VALID and say different things. The **clearance aggregate is one verdict**, not three checks: fee dues (through `LedgerService.outstandingFor`, the single dues source), library loans and fines, and a hostel bed still held — and a source that could not be **read** is reported `incomplete` and never as clear, because a failed read returns the same "nothing" a settled account does. Clearance **gates the TC and, by default, only the TC** (`documents.clearance_required_types`): the transfer certificate is the document that ends the relationship, while refusing to say a child is of good character over unpaid tuition is a different and meaner act. Every other type still **reports** what is owed. Issuing a TC marks the student TRANSFERRED behind an explicit confirm flag, and the status change is attempted *after* the certificate commits — a side effect never rolls back the act that triggered it (M20/M21). **The Office Staff issues certificates and may neither revoke one, waive clearance, backfill the register, nor delete from the archive** — the M16/M20/M21/M23/M24/M25/M26 rule, continued into the counter.
- **Complaints, visitors & alumni (M28):** an **anonymous complaint is anonymous at the database** — no raiser id, no contact, **no IP** — and the per-IP hourly cap that guards the public form is therefore not applied to one, because an IP is a contact detail; the captcha and the route throttle carry that load instead. Nothing can notify an anonymous complainant because there is nothing on the row to notify. A **restricted complaint is invisible rather than forbidden**: a caller without `ticket.sensitive.view` gets the same 404 an unknown id gets, never appears to be refused, and the row never enters their listing or their report — and the report **says on its face** that it could not see them (the M27 lesson that a shape must state what it could not read). Sensitivity is decided once at creation and stored, so narrowing the setting later cannot expose what was already filed. **Only the assignee or an inbox manager moves a status** (the code is checked at the route, the *relationship* in the engine), a **REOPEN is allowed within seven days of `closed_at`**, and a reopen clears the resolution and the SLA stamp but **keeps the rating** — clearing it would let a school lift its satisfaction average by reopening what people scored badly. **The gate register's truth is a predicate**: `check_out IS NULL` is the in-building list, the day-end sweep writes both a time and a flag saying a machine wrote it, and a **multi-day pass is OFFICIAL-only** and bounded. The **alumni directory publishes only opted-in, approved profiles and never a contact detail**, behind two locks — the query and the shape; a **claim on an already-claimed student record may be registered but not approved** (roadmap §8's conflict queue, which is the PENDING rows plus a partial unique). **A donation receipt is immutable**: no update path, a correction is a cancellation carrying a reason, the row stays in the register, and the M20 voucher **stands** because reversing a posted entry is the accountant's act (the M24/M25 rule); a gift **in kind** is receipted and reported but never debits cash. Over capacity on an event **warns** (the M25 bus rule). **The Office Staff runs all three desks and holds neither `ticket.sensitive.view`, `ticket.delete` nor `alumni.donation.cancel`** — the M16/M20/M21/M23/M24/M25/M26/M27 separation, continued into the front office.
- Soft delete everywhere except append-only logs (audit, ledger, login activity, notifications, sms credits, **pf ledger**, **ticket comments**) and `voucher_entries` / `salary_components` (hard-deleted with their parent) — plus `assignment_submissions`, which has no `deleted_at` because it is replaced in place (M22).
- Timezone: store UTC, display Asia/Dhaka; weekly holiday configurable (default Friday).

| School logo stored as S3 key, URL signed on every read | signed URLs expire (1 h); the key is the stable reference | M04 |
| Settings secrets envelope `iv.tag.cipher` (AES-256-GCM) | GCM authenticates — tampered rows fail closed to registry defaults; key rotation = re-enter secrets | M04 |
| Health disk probe Linux-only | `check-disk-space` needs `wmic`, gone on modern Windows 11; prod is Linux | M01 |
| shadcn `field.tsx` instead of legacy `form.tsx` | new shadcn registry deprecated the form wrapper; `FormDialog` uses RHF `FormProvider` directly | M01 |
| Repository pattern over Active Record / direct ORM in services | data access isolated from business logic; swappable/testable (mock repos in unit tests); single place to enforce soft-delete + tenant scoping | M01 (owner decision) |
| shadcn/ui as component library | vendored components (full control, no lockstep upgrades), Tailwind-native, RHF/Zod-friendly | M01 (owner decision) |
| `school_id` on all tables from day one | Module 31 SaaS without rewrite | M01 |
| Refresh in httpOnly cookie (web) | XSS-resistant; body-based reserved for mobile | M02 |
| Permissions NOT in JWT | instant revocation via Redis cache (5 min TTL + explicit invalidation; DB fallback when Redis down) | M03 |
| All APP_GUARDs declared in AppModule (JwtAuthGuard moved out of AuthModule) | global-guard execution = provider registration order; root registers before imports, so cross-module ordering is only guaranteed in one providers array | M03 |
| `audit_logs.action` VARCHAR, id BIGSERIAL, no FK to users | verbs grow per module without enum migrations; table stays partition-ready for M30 retention | M03 |
| Audit writes fire-and-forget | auditing must never delay/fail the mutation; failures logged | M03 |
| `RbacModule` re-provides `UsersRepository` instead of importing AuthModule | AuthModule imports RbacModule for /auth/me — keeps the module graph acyclic (repos are stateless) | M03 |
| Calendar dates as `@db.Date` + YYYY-MM-DD strings end-to-end | no timezone ambiguity; strict `parseDate` round-trip catches regex-shape-valid but impossible dates (`2026-13-99` reached Prisma as Invalid Date before) | M05 |
| Holidays hard-deleted, events soft-deleted | per roadmap spec — cancelling a holiday removes it (audit trail keeps history); events keep the standard business-entity lifecycle | M05 |
| Weekly off-days = M04 setting, not holiday rows | one source of truth, per-school configurable; `isHoliday` merges setting + ranges | M05 |
| `src/modules/academic/` namespace shared by M05+M06 | sessions/calendar and classes/sections/subjects are one domain; avoids `academic-*` module sprawl | M05 |
| COALESCE unique indexes for nullable identity columns | Postgres treats NULLs as distinct — `uq_sections_identity`/`uq_class_subjects_identity` map NULL shift/group to the nil UUID inside the index | M06 |
| `<entity>.manage` permission granularity for structure masters | no real-world role splits create vs delete for a shift/department; reads share one `structure.view` | M06 |
| Prisma model `SchoolClass` for table `classes` | `class` is a TS keyword in generated client code | M06 |
| e2e suites run serially (`maxWorkers: 1` in jest-e2e.json) | every suite (15 as of M15) shares ONE dev DB/Redis/Mailpit — parallel workers caused cross-suite flakes. The corollary, learned in M14: a suite must not assert on process-wide state such as heap, which accumulates across the run | M06 |
| Grading snapshot copied into results | grade-system edits never mutate published results | M04/M15 |
| **The grade scale freezes at the FIRST processing run, not at PUBLISH** (revises M14) | M14 froze `exams.grading_snapshot` at publication, but results are computed during PROCESSING — so they were graded through the *live* table, and a band edited between processing and publication would freeze a scale no result on file was ever computed against. Freezing at first use makes the scale a result was graded through the scale that gets published | M15 |
| Publication is a versioned row, not an exam status | M14's status machine deliberately cannot rewind past PUBLISHED (a published result is corrected by re-issue, not by a quiet column rewind), so "unpublish" needed its own switch. A partial unique index keeps exactly one active version, because every reader resolves "the" active publication | M15 |
| `ResultReadinessGate` is consulted in `publish()` as well as via the status machine | found by the M15 e2e suite: the publication row was committed *before* `changeStatus` asked the gate, so a refused publish left an ACTIVE publication live — and a **republish** never reaches the status machine at all, so it was never gated. Checking at the top of `publish()` covers both | M15 |
| Per-component pass thresholds override the band table | the grade bands only see the total, so an 88/100 with 8/25 in a practical against a bar of 10 would print A+. The engine forces the failing band instead — which is what a BD board does | M15 |
| Grace marks are a budget, applied in a second pass | which subjects deserve grace can only be decided once every subject is evaluated ("grace in at most one subject" is an allowance across the exam, not a per-subject entitlement); the cheapest deficits are bought first, which is what a school means by grace | M15 |
| `marks.grade`/`grade_point` are written only by a processing run | a mark by itself has no grade — the scale it is read through is a property of the run. Re-entry and corrections clear them, so a report card can never print an A+ beside a mark that no longer earns one | M15 |
| Merit is a second pass, and a single-candidate reprocess re-ranks everyone | positions are relative: one corrected mark can move a student past three classmates, and leaving the others untouched would publish two students at the same rank with a gap above them | M15 |
| A missing mark yields INCOMPLETE, never a zero | the school has not finished marking; a zero would rank the student against fully-marked classmates and fail them for the office's backlog | M15 |
| A WITHHELD result survives re-processing | withholding is an administrative decision about a person, not an arithmetic outcome — a re-run of the maths must not quietly release it | M15 |

| Clearance gates the TC and, by default, **only** the TC | Roadmap §6 makes the rule about the transfer certificate, and the reason is that it is the document that *ends the relationship* — the last moment the school has any leverage to get its textbooks and its fees back. A character certificate is a reference, and refusing to say a child is of good character because their family owes two months' tuition is a different and meaner act that a system should not make the default. So `documents.clearance_required_types` defaults to `["TRANSFER"]`, a school may widen it, and an ungated type still **reports** what is owed on the wizard's panel — only `allowed` changes | M27 |
| **A clearance source that could not be READ never reports the student as clear** | The defect this prevents is invisible: a failed read returns no amount and no items, which is *indistinguishable* from a source that answered "nothing owed" — so a library that is down would have read as a student who had returned every book, and the verdict would have said CLEARED with a transfer certificate going out over an unreturned textbook. `ClearanceSourceInput.incomplete` makes the difference explicit. It **warns rather than refuses**, because a school must still be able to issue a character certificate while another module is misbehaving (the M25 "nothing in the fee source ever throws" rule), and `complete: false` is what the panel and the stored snapshot record | M27 |
| DUPLICATE and CORRECTION are separate enum values because they have **opposite** preconditions | A duplicate reprints a certificate that is still *valid* (the family lost their copy) — duplicating a revoked one would put a document the school has disowned back into circulation under a fresh number. A correction replaces one that is *not* valid — issuing it against a live certificate would leave two contradictory documents both verifying VALID, which is the exact failure the verification page exists to prevent. One "reissue" flag would make getting it backwards a matter of convention | M27 |
| REVOKED is reported publicly; a DRAFT is NOT_FOUND | Saying "no such certificate" about a revoked one would make a forger's document and a genuinely cancelled one look identical to whoever is checking, and the school's own reason is the useful half of the answer. A draft is the opposite case: it has no public existence at all, and answering anything but the unknown-code answer would confirm that something the caller may not see exists — the M15 public-result-search / M19 draft-preview rule | M27 |
| The verify code is **Crockford Base32**, and the confusable fold is the point | `I`, `L`, `O` and `U` are absent and the first three fold onto `1`, `1` and `0` when somebody types what they read off a laser print or a photocopy. A verification page that answers "not found" to a *correctly-read* certificate is worse than having no verification page — it tells the holder of a genuine document that it is a forgery. 32 divides 256 exactly, so the modulo is unbiased and rejection sampling would add a loop with nothing to test; a 29-character "unambiguous" alphabet would have lost both properties | M27 |
| The prize wizard cuts on **position**, not on count | M15 ranks by competition (1, 2, 2, 4). "Top 3" with a shared second place is four students, and truncating the list at three would hand one of two tied children a prize on no basis anybody could explain to their parents. The wizard reports when the count differs from what was asked for, and it **always previews first** — a run that raised two hundred certificates before showing anybody the list would be corrected by *revoking* two hundred certificates, each a permanent register row with a number that can never be reused | M27 |
| The certificate PDF renders the body as TEXT, through M19's `htmlToText` | pdfkit has no HTML engine. The honest options were a headless-browser dependency (a Chromium process per print, on a school's VPS) or a converter that silently drops half of what an editor wrote. M19's own converter is already golden-tested and gives a faithful, predictable page: paragraphs survive, tables and floats do not. The limitation is stated on the screen where a template is written rather than discovered on a printed certificate — the same trade M09 made for ID cards | M27 |
| The archive **soft-deletes and keeps the S3 object**, unlike M07/M09 documents | Those tables hard-delete the object with the row, and rightly: they hold a person's paperwork, uploaded by whoever manages that person, and a deletion means "this was the wrong file". An archive is the *school's record* — a removal is an administrative act, `archive.delete` is a permission the office deliberately does not hold, and a restore has to be possible from the row alone | M27 |
| Deleting an archive folder is refused while anything is inside it | A cascade would be the convenient implementation and is exactly wrong for a filing cabinet: a mis-clicked delete that silently took forty scanned circulars with it is not recoverable by anybody who was not watching. The message names what is in the way and how much of it | M27 |
| A query-string array is normalized in the DTO, not assumed | Found by the M27 e2e suite: `@IsArray()` alone 400s on `?tags=board`, because a single query parameter is a **string** — and the bracket form that would parse as an array depends on the Express query-parser mode, which is not something a caller can see. The transform accepts one value, a comma-separated list and a repeated parameter, resolving the ambiguity where it actually is rather than in every client | M27 |
| `String(unknown)` is never used to build a stored snapshot | Caught by `@typescript-eslint/no-base-to-string`: a blanket `String(value)` prints `[object Object]` for anything non-scalar — and on a certificate that string would have been **frozen there forever**. The helper coerces only scalars (matching M17's `template.engine` `coerce`), and a non-scalar renders blank where `missingFields` reports it on the review step, before the paper is printed | M27 |
| **Anonymity is enforced at the database, not at the form** | A school that offers an anonymous complaint box and then stores the sender's phone number beside the complaint has not offered one; it has built a trap, and the person who trusted it finds out too late. `chk_tickets_raiser` refuses an ANONYMOUS row carrying a raiser id, a contact block **or an IP**, so the service cannot leak one by forgetting. The consequence is accepted deliberately: an anonymous submission is **not** IP-rate-limited, because an IP is a contact detail — the captcha and the route throttle carry that load | M28 |
| A restricted complaint answers **404, never 403** | Roadmap §8 keeps a complaint naming a member of staff away from general staff. A 403 tells that member of staff a complaint about them exists, which is precisely the disclosure being prevented — so the row gives the same answer an unknown id does and never enters the listing. The M15/M19/M22 rule ("a read must not confirm what the caller may not see") applied to a person rather than to content | M28 |
| Ticket sensitivity is **stored at creation**, not derived on read | Deriving it from the live category list would mean that narrowing `community.ticket_sensitive_categories` retroactively exposes complaints already filed. The people who wrote those were told they would be handled discreetly, and a settings edit is not their consent | M28 |
| The SLA is a **map from priority to hours**, not the roadmap's single 72 | A broken toilet and an allegation about a teacher do not deserve the same clock; one threshold means either the urgent case waits three days or every suggestion pages the head overnight. MEDIUM keeps 72, so a school that never touches the setting gets exactly the specified behaviour | M28 |
| A rating **survives a reopen** (and the CHECK permits it) | Found by the e2e run as a 500: the status-evidence CHECK allowed a score only on RESOLVED or CLOSED. REOPENED is the state that means "there *was* a resolution and it did not hold", so a rating belongs on it — and clearing the score instead would let a school lift its average satisfaction by reopening the tickets people scored badly | M28 |
| The gate register has **no visitor status column** | `check_out IS NULL` IS the in-building list, so nothing exists that can fall out of step with it. The M26 bed-status lesson inverted: where an index or a predicate can be the truth, a column should not try to be | M28 |
| The day-end sweep writes a **flag as well as a time** | "Left at 16:40" and "was still signed in when we locked up" are different facts. A register that showed them identically would be useless for the one question — a fire drill, a safeguarding review — it would ever be pulled out for. The M12 "an unmarked day is not an absence" reasoning, at a gate | M28 |
| Roadmap §8's alumni **conflict queue needs no queue table** | A second person claiming a student record registers and sits PENDING — that *is* the queue, and reviewing it is exactly the human judgement the situation needs. What is refused is the **approval**, by a readable service message and by `uq_alumni_student` (partial: APPROVED, live rows) underneath it, so two people can never both be approved as the same person | M28 |
| Alumni match hints **rank and never link** | "Md. Rahman, batch 2015" describes several real people at any BD school of size. The engine scores a phone match above a name (a number is what the school actually held for five years) and normalizes the honorifics a BD register carries, then stops — anything cleverer would start being trusted | M28 |
| A **gift in kind is receipted but never debits cash** | Twenty donated benches are worth twenty thousand taka on the receipt and in the accounts, and are not twenty thousand taka in the cash box. Posting them there would make the ledger disagree with the tin the first time anybody counted it; *what* was given decides which asset account it belongs in, and the alumni desk cannot know that | M28 |
| Cancelling a donation **leaves its voucher standing** | Reversing a posted entry is the accountant's act and `voucher.cancel` is not this module's permission — the M24 purchase-cancellation and M25 vehicle-expense precedent, verbatim. A module that quietly reversed ledger entries on somebody else's behalf would be the second place in the system with an opinion about the books | M28 |
| The complaints board is **read-only; the drawer does the work** | Dragging a card to RESOLVED is the natural gesture and the wrong one: the DB CHECK refuses a resolved ticket with no resolution, so the gesture would either pop a dialog anyway or write an empty one. The status changes where the words are | M28 |

| **The report registry stays a FILE; `report_definitions` is its projection** | Roadmap §3 says the table "replaces the code-only registry from Module 18", and it replaces its *storage*, not its authority. Rows a developer inserts by hand get no code review, no diff, and no way for `tsc` to notice a report pointing at a permission nobody defines. The seeder syncs the file exactly as `rbac.seeder` syncs permissions, down to `is_orphaned` — never a delete, because `report_schedules` and `report_runs` carry a foreign key to `code` and a school's Monday-morning email may not vanish because somebody renamed something. What the table genuinely buys: a real FK, and a queryable `params_schema` the hub auto-generates its form from | M29 |
| **Every report returns the SAME `ReportTable`**, and one renderer serves all 55 | The obvious alternative is what M12–M28 already have: an export service per module, each with its own columns, styling and page setup. That is fine for one module and fatal for a framework — §6's column stripping and §8's streaming both need a single place to happen, and forty-odd bespoke writers have forty-odd places | M29 |
| **A sensitive column is STRIPPED, not a reason to refuse the report** | Roadmap §6 says "engine strips columns otherwise" and the emphasis is the design. Refusing is the obvious implementation and is wrong: a payroll clerk who may see net pay but not tax details still needs the register, and a nurse building a class list should not be told "denied" because one column is medical. The cells are **deleted rather than blanked** — a blanked column still discloses that the field exists and how many rows have one, which for a medical flag is most of the disclosure — and the report **says which columns went**, so a short sheet reads as a permissions boundary rather than a broken export | M29 |
| The engine re-checks permissions on the worker side | Not belt and braces: a **scheduled** run has no request, no guard and no route, so the engine's check is the only authorisation that ever happens. §6's "engine-level, not just UI" is not a nicety in that path, it is the entire enforcement | M29 |
| **The cron parser IS the whitelist** | §7's rule ("no sub-hourly") is a *refusal*, and a library that accepts a five-minute step and then fires a full-school tabulation twelve times an hour has enforced nothing. So the parse and the validation are one function, and one condition carries the rule: the minute field must be a single literal 0–59. Sub-hourly becomes unrepresentable rather than discouraged. Six-field (seconds) expressions are refused rather than silently reinterpreted, because the two dialects disagree about which field is which and the mistake is invisible | M29 |
| Vixie's day rule: both day fields restricted means **OR**, not AND | `0 9 1 * 1` fires on the 1st *and* every Monday. Getting it backwards turns a monthly schedule weekly (or skips six weeks), and nothing about the expression looks wrong | M29 |
| A schedule is **DISABLED with a reason**, which is a different state from PAUSED | PAUSED is the owner's choice and ACTIVE undoes it. DISABLED is the system's — §6's exhausted retries or §8's departed owner — and the `disabled_reason` CHECK is what stops the two being confused. A schedule that silently stopped emailing is worse than one that never existed: the school goes on believing the report arrives | M29 |
| An orphaned schedule is disabled, **never deleted** | The school may well still want the report, and somebody has to be able to see what was being sent and to whom. Checked on the sweep rather than hooked to user deletion — a hook would need Auth or Staff to import AnalyticsModule, a cycle waiting to happen for a rule that is not urgent (the engine already authorises a departed principal as nobody) | M29 |
| `mv_collection_monthly` is a **FULL OUTER JOIN of two aggregates**, not one `GROUP BY` | An invoice belongs to its billing month and a payment to the day the money arrived; a March invoice settled in May is normal and common. One join would multiply the invoice total by its payment count — the classic fan-out — and would also drop a month that had payments but no invoices | M29 |
| `mv_result_summary` filters on `published_at`, not on a status | `result_status_enum` is PASSED/FAILED/INCOMPLETE/WITHHELD: it describes the candidate, not the release. WITHHELD is excluded on top, because a trend that moves when somebody's dues are cleared is not measuring what the reader thinks | M29 |
| The enrollment trend counts from **dates**, never from `status` | `status` is *now* and a trend is *then*. Everybody promoted last year is PROMOTED today, so an `ACTIVE` filter would report last year's roll as empty and draw a chart claiming the school had no students until April. An enrollment has no leaving date, so the window is `[enrollment_date, session end]` with CANCELLED excluded | M29 |
| A heatmap cell with no data is **null and never 0** | A section that did not exist in April and a section that recorded 0 % in April are different facts, and painting them the same colour is worse than omitting one — the reader cannot tell. The colour scale is computed over the cells that *have* a value, so the gaps do not drag it to the floor | M29 |
| Everything served from a materialized view **prints its own staleness** | Roadmap §8 asks for the eventual freshness to be documented on affected reports; in a UI "documented" means on the panel. A figure that quietly disagrees with the live screen beside it destroys confidence in both, and nothing on the page says which is older | M29 |
| Fee realization is **not capped at 100 %** | A month that settled last term's arrears genuinely collected more than it billed, and clamping would hide exactly the recovery the accountant is looking for | M29 |
| **Page views are counted by a beacon, not by API middleware** — roadmap §3 said "decide" | §3's default suggestion was a server-side counter on the public routes, and it would report wrong numbers invisibly: a Next-rendered page makes between zero and five `/public/*` calls depending on the route, so the notices page would show five times the homepage's traffic while the homepage — which fetches nothing — showed none. The public layout fires one beacon per navigation instead. The price is explicit: a reader with JavaScript off is not counted, which understates traffic slightly and never distorts its shape | M29 |
| **Unique visitors live in a HyperLogLog; no visitor identifier is stored** | A visitors table keeps IP addresses and a Redis SET of fingerprints keeps a reversible list of them. M28 already settled that an IP is a contact detail — it refused to rate-limit anonymous complaints by IP for that reason — and a marketing-page counter is a far weaker justification than a complaint box was. The fingerprint is a salted SHA-256 of IP + user agent fed into a fixed ~12 KB structure no member can be read out of, and is never written down. `analytics.website_visitor_salt` is a **secret** setting: readable, it would let anyone compute the hash for a given IP and test membership — the exact linkability the HLL was chosen to prevent. The consequence is stated on the API: **daily uniques cannot be summed into a window total** | M29 |
| A run's S3 **bucket and key are stored beside the signed URL** | A signed URL expires and cannot be used to find the object again, so a system keeping only the URL leaks every export file it ever made. The retention job deletes the object **first** and the row second — a failure then leaves the row for the next sweep rather than orphaning the file | M29 |
| A re-run is authorised as **whoever pressed it** | Otherwise re-running somebody else's payroll export would be a way around `payroll.report`. The ownership check applies too: a run you may not open is not one you may clone, because its stored parameters are themselves a disclosure (which class, which account, which month somebody was looking at) | M29 |
| Two `@Query()` DTOs on one handler is a **400 on every request** | Found by the M29 e2e run. `forbidNonWhitelisted` validates each bound DTO against the whole query string, so a pagination DTO and a filter DTO each reject the other's keys. `PaginationQueryDto`'s own comment says "extend per module" for exactly this reason — worth remembering on any new paginated handler | M29 |
| A window is not always a date pair | Also found by the e2e run: M21's payroll reports are grained in **months** and appended `-01` to what they assumed was `YYYY-MM`, producing `"2026-08-01-01" is not a valid calendar date`. Both are `string`, so nothing structural could catch it — `defaultMonthWindow` and a `month`-typed registry param now carry the distinction | M29 |

## 18. Outstanding Technical Debt

- **Cross-cutting — list pickers truncate at 100 (QA finding F31):** every list endpoint caps `limit` at `MAX_PAGE_LIMIT = 100` and **rejects** anything larger with a 400 rather than clamping. Fourteen frontend pickers asked for 200–300 and therefore rendered **empty**, silently — including the routine builder's "combined with" picker and the promotion wizard's target sections. All fourteen now request `MAX_PAGE_LIMIT`, mirrored in `src/lib/constants/pagination.ts` with a Vitest guard that reads the backend constant and asserts the two still agree. **The remaining debt:** 100 is a ceiling, not a page size — a school with more than 100 sections, alumni or inventory items still needs a searchable or paginated picker rather than a silently truncated list.
- **Cross-cutting — date display and "today" (QA findings F24/F25/F29, fixed):** three separate mistakes with one root, that a machine-format date reads plausibly. (a) Raw ISO rendered to users in 24 places, including a **student ID card**; (b) day boundaries built in UTC, so an admission cycle closed six hours late in Dhaka; (c) `new Date().toISOString().slice(0, 10)` used as "today", which is **yesterday between midnight and 6 AM Dhaka** — it dated certificates, admissions and routine effective-dates a day early. Now guarded on both sides: `no-unlocalised-dates.test.ts` knows four shapes of the display bug, `no-utc-today.spec.ts` bans the UTC "today", and `e2e/sweeps/dates.spec.ts` checks the **rendered page** for ISO dates — the one guard that needs no knowledge of field names, and the one that caught `effectiveFrom`.
- **M12 — attendance percentages had two denominators (QA finding F28, fixed):** `percentage` appeared twice in one student report with different meanings (42.86% and 60%), because range-spanning figures were computed by a private service helper dividing by *marked days* while the engine divided by *working days*. The school-wide figure separately read **100%** where the honest number was 7.14%, having no headcount in its denominator. The arithmetic now lives in `calc/percentage.util.ts` as three named functions — `sameDayPercentage`, `rangePercentage`, `cohortPercentage` — with nine golden cases. **Per-day figures legitimately divide by marked students**; only the range-spanning ones were wrong.

- **M02 — needs an owner decision (QA finding F2):** the two-tab rotation grace leaves **2–3 live refresh tokens per browser login**, so the session manager shows phantom devices and "sign out this device" may not actually end the session. Mechanism confirmed: tab A refreshes `T1` → gets `T2` and marks `T1` revoked/replaced; tab B presents the same `T1` inside `ROTATION_GRACE_MS`, and `rotate()` issues `T3` but skips chaining because its `if (!oldRecord.revokedAt)` guard is already false — so nothing is retired. Both obvious repairs are worse than the bug: revoking `T2` when issuing `T3` makes tab A's next refresh trip **reuse detection and revoke every session for that user** (a logout storm from an ordinary two-tab load), and re-issuing the existing replacement is impossible because only its hash is stored. The correct fix is a **session/lineage id shared by rotated tokens**, with the UI grouping by it and revocation retiring the lineage — a schema column and a migration. Deliberately not patched during browser QA.
