## 1. Current Architecture

- Two repos: `hexschool-frontend` (Next.js 16, TS, App Router, Turbopack), `hexschool-backend` (NestJS 11, TS). (Product branded HexSchool; DB/bucket keep the `smis` name.)
- **ORM: Prisma 7** (owner decision in M02, replacing TypeORM). Schema in `prisma/schema.prisma`, CLI config in `prisma.config.ts`, runtime via `@prisma/adapter-pg`; migrations: `npx prisma migrate dev|deploy`. Partial indexes/CHECKs are hand-written into migration SQL (`--create-only`, then edit).
- PostgreSQL 16+ single database (team dev DB currently on Neon; compose postgres remains for local use); Redis for cache + BullMQ queues; S3-compatible object storage (MinIO in dev).
- Frontend global state: **Redux Toolkit** (owner decision in M02; roadmap originally said Zustand) — per-tab store via `StoreProvider`, typed hooks in `src/lib/store/hooks.ts`. Server state stays in TanStack Query.
- Next 16 note: middleware is `src/proxy.ts` (renamed from middleware.ts) — optimistic route guards via the non-sensitive `hs_session` hint cookie; real enforcement is always API-side.
- REST API under `/api/v1` (port 4000), Swagger at `/api/docs` (basic-auth in prod); Bull Board at `/admin/queues` (basic-auth always). Frontend dev on port 3000.
- Dev infra via `hexschool-backend/docker-compose.yml`: postgres:16 (host port **5433** — 5432 is taken by a native install on the dev machine), redis:7, MinIO (9000/9001), Mailpit (1025/8025).
- Single-school deployment now; **every business table carries `school_id`** so Module 31 can activate multi-tenancy without schema surgery.
- Docker Compose for dev (postgres, redis, minio, mailpit, backend); Nginx + Docker on Ubuntu for prod (formalized in Module 30).

## 2. Folder Structure

**Backend** — `src/modules/<name>/{entities,dto,controllers,services,repositories,guards,policies,events,jobs}` plus `src/common/{filters,interceptors,pipes,decorators,utils}` and `src/config`.

**Frontend** — route groups: `src/app/(public)` website, `(auth)` login flows, `(admin)` panel, `(portal)` student/parent/teacher, `(platform)` reserved for Module 31. Shared code in `src/components/{ui,shared}`, `src/lib/{api,validations,utils,hooks}`.

## 3. Naming Conventions

- DB: snake_case, plural tables, UUID PKs (`gen_random_uuid()`), constraint prefixes `fk_/uq_/idx_/chk_`.
- API: kebab-case plural resources (`/fee-invoices`), camelCase JSON fields.
- Code: PascalCase classes/components, camelCase functions/vars, TS enums mirroring PG enums.
- Document number patterns (all sequence-table backed, per school, gap-free in transaction): `{SCHOOL_CODE}-S-{YY}{SEQ4}` staff, `{SCHOOL_CODE}-{YEAR}{SEQ5}` students, `ADM-{YY}-{SEQ6}` applications, `INV-{YY}{MM}-{SEQ6}` invoices, `DV/CV/JV/CN-{YY}-{SEQ}` vouchers, `TC-{YY}-{SEQ4}` certificates (per type).

## 4. Coding Standards

- Strict TypeScript both repos; ESLint + Prettier + Husky (lint, typecheck, test pre-commit).
- No `any` without justification comment; no raw SQL outside repositories; no unscoped (missing `school_id`) queries.
- Backend business rules live in services (controllers thin); pure calculation engines (results, payroll) are dependency-free and golden-tested.
- **Repository pattern:** all data access goes through per-entity repository classes extending `BaseRepository` (generic CRUD, pagination, soft-delete + `school_id` scoping, `withTransaction`). Services never touch the ORM/QueryBuilder directly; controllers never touch repositories. Flow is strictly Controller → Service → Repository.

a `SENT`/`DELIVERED` row must carry `sent_at`, a `FAILED` one an `error`; a `dedupe_key` partial-unique collapses a repeat within a window). `notices` (audience + scheduled `publish_at` + website-visibility) feed the board; `sms_credits` is the **append-only** running-balance ledger the dispatcher decrements per SMS part (`balance_after` pinned ≥ 0). **Live since M19:** nine website tables sharing ONE publication enum (`web_content_status_enum`), so "only PUBLISHED is public" needs no per-table exception: `cms_pages` and `news_posts` (slug unique per school among live rows via a partial unique; a PUBLISHED row must carry `published_at` by CHECK, because it is both the feed sort key and the RSS `<pubDate>`), `galleries` →1:N→ `gallery_items` (**hard-deleted** — an album's items are replaced as a set, the M13 `timetable_entries`/M14 `seat_plan_entries` precedent), `downloads` (`download_count` is the one column an anonymous visitor may move, and only upward), `careers` →1:N→ `career_applications`, `faqs`, `committee_members`, and `contact_messages` (a REPLIED row must carry `replied_at` and anything past NEW a `read_at` — the M16/M17 evidence rule; a CHECK also refuses a message with neither phone nor email). **Live since M20:** `accounts` is a tree per school inside five fixed groups (`account_group_enum`), where `is_group` marks a **heading** — a subtotal that holds no money, pinned by `chk_accounts_group_node_empty`, because only leaves may be posted to; `is_system` marks the five accounts auto-posting resolves to, which may be renamed but never deleted or deactivated. `vouchers` →1:N→ `voucher_entries` (**hard-deleted** with their voucher and replaced as a set while DRAFT — the M13/M14/M19 wholesale-replacement precedent), each line one-sided and non-negative by `chk_voucher_entries_one_sided`; that Σdebit = Σcredit *across* a voucher is deliberately **not** a trigger (a CHECK cannot see siblings) and lives in `voucher.engine.ts`. A POSTED voucher is immutable: `cancel()` marks it CANCELLED and writes a mirror-image reversal linked by `reversal_of_voucher_id`, and **both stay in the ledger** — reports read `posted_at IS NOT NULL`, not `status = 'POSTED'`. `vouchers.source_ref` is the auto-posting idempotency key (partial unique excluding CANCELLED), and `chk_vouchers_source_ref_shape` makes a MANUAL voucher never carry one. `posting_maps` (kind × ref_key → account, append-only kinds), `budgets` (session × account × optional month, COALESCE identity index) and `fiscal_periods` (non-overlapping, CLOSED locks everything dated inside). **Live since M21:** `leave_types` is a TABLE (it **replaced** `leave_type_enum`, because a taxonomy carrying an annual quota, a carry-forward cap and a paid/unpaid flag is data) →1:N→ `leave_balances` (one row per person × type × session, `uq_leave_balances_identity`, `used` moved only by the approval flow) and `leave_applications` — the polymorphic successor to M08's `teacher_leaves`, which the M21 migration **copied across and dropped**. An application stores its `days` rather than deriving them, because the working-day calendar it was counted against can be edited afterwards and an approved leave must not start consuming a different amount of quota. `salary_structures` →1:N→ `salary_components` (**hard-deleted** and replaced as a set — the M13/M19/M20 wholesale-replacement precedent). `employee_salaries` is **history**: a change writes a NEW row with an `effective_from`, and `uq_employee_salaries_identity` keeps exactly one row per person per date so "the salary in force on 1 March" has one answer. `payroll_runs` (one live run per month, the partial unique excluding CANCELLED so a cancelled run frees the month — the M11 rule; `month` pinned to the 1st by CHECK, or the unique would compare something other than what it claims) →1:N→ `payslips`, every figure **stored** rather than recomputed (the M14/M15 snapshot rule) with a `breakdown` JSON that carries the engine's input snapshot, so an edit-with-reason recomputes exactly, months later, through the same engine. `bonus_runs` are rules resolved per person at generation. `pf_ledger` is **append-only** with a running `balance_after` (the M17 `sms_credits` pattern), one CONTRIBUTION row per payslip behind a partial unique. `teachers` and `staff_profiles` gained `exit_date`, because M07/M08 recorded a status *change* but never its date and payroll cannot prorate a leaver's final month without one. **Live since M22:** `assignments` = one piece of work for a (session, section, subject) set by a teacher, walking `DRAFT → PUBLISHED → CLOSED` with `published_at`/`closed_at` as the evidence (`chk_assignments_status_evidence`) and `due_at > assigned_at` pinned by CHECK; both timestamps are wall-clock **instants** rather than dates, because "due Thursday" at a BD school means a time of day and 23:59 vs 00:01 is exactly what `is_late` decides. `due_reminder_sent_at`/`no_submission_alert_at` are the two jobs' idempotency (the M12 `absent_notified_at` column-as-dedupe pattern). →1:N→ `assignment_submissions`, keyed on **`enrollment_id`** like every other academic record and carrying **no soft delete** — a resubmission replaces the row in place so the evaluation hanging off its id stays attached (the M15 `marks` rule), which is also what lets `uq_assignment_submissions_identity` be a PLAIN unique rather than a partial one; `chk_assignment_submissions_content` refuses a row with neither text nor a file, because an empty "submission" would land on the teacher's grid as handed-in and inflate the one percentage this module exists to report. `is_late` is **stored**, not derived (see §16). `learning_materials` hang off a class with an **optional** section, where NULL means class-wide — which is why `class_id` is stored alongside rather than read through the section, why the visibility query writes the NULL branch out explicitly, and why that FK is `ON DELETE RESTRICT` rather than Prisma's default SET NULL for an optional relation (a deleted section would otherwise silently promote a private material to the whole class). `chk_learning_materials_link_scheme` pins `link_url` to `https://…` at the database, because that column is rendered as an anchor in a student's browser. **Live since M23:** the library separates the **title** from the **copy**, and everything follows — `books` (bibliographic; `isbn` nullable and deliberately NOT unique, because a BD school’s shelves carry unISBN’d local guides, duplicate donations and reprints that never changed their number — a checksum is validated on write instead) over `book_categories`/`authors`/`publishers`, with `book_authors` **hard-deleted and replaced as a set** (the M13/M19/M20 precedent). `book_copies` is the physical volume, and `uq_book_copies_accession` **ignores `deleted_at`**: an accession number is a barcode label stuck inside a book and is never reused, exactly as an employee ID (M07) or a student UID (M09) is never reused; `uq_library_members_card` is the same rule for a printed card. `library_members` is polymorphic over `students`/`teachers`/`staff_profiles` with no FK (the M12 `staff_attendances` / M21 `leave_applications` precedent), and `max_books` is **stored on the card** rather than read from settings at issue time, so an exception granted to one student survives a later edit of the school-wide default. `book_issues` carries **no soft delete** — a loan is history and a wrongly-issued copy is returned, not erased — which is what lets **`uq_book_issues_open_copy` (`WHERE returned_at IS NULL`)** make “one physical book, one pair of hands” true no matter what a service forgets. Its money columns are the module’s ledger: `fine_amount` assessed, `fine_collected` + `fine_waived` the two ways it goes away, and **`fine_paid` DERIVED by `chk_book_issues_fine_paid`** rather than assigned (the M16 `deriveStatus` rule pinned at the database — the one invariant a “mark as paid” button could otherwise break); `chk_book_issues_waiver_evidence` refuses a write-off with no name and no reason on it, and `overdue_days`/`holiday_days` are **stored** so editing the calendar later cannot make a settled fine disagree with the receipt already handed over. `book_reservations` is a queue on a **title** — `reserved_at` IS the rank, so a cancellation never rewrites anybody’s position — and the copy status is its shadow (a copy is RESERVED exactly while a READY hold points at it, `uq_book_reservations_held_copy`). `stock_verifications` →1:N→ `stock_verification_scans` (hard-deleted with the parent) hold a physical count whose **expected set is resolved at CLOSE, not at open** (a book issued mid-count is legitimately absent) and whose diff is then **frozen into the row** (the M14/M15 snapshot rule). **Live since M25:** `vehicles` (the three expiry dates are the module's most load-bearing columns — an unfit or uninsured bus full of children is the thing it exists to stop happening quietly — and `uq_vehicles_reg_no` is unique among **live** rows, the OPPOSITE of the M07/M09/M23 never-reuse rule, because a plate is issued by the BRTA and belongs to the vehicle rather than to the school's numbering) and `drivers` (`staff_id` optional — a BD school's driver is as often the contractor's as the payroll's — with a live-rows unique on the licence and one driver row per employee). `routes` carry a vehicle, a driver, an optional **substitute** (roadmap §8's temporary replacement, a field rather than a rota) and a helper; `chk_routes_shape` refuses driver = substitute, because the substitute exists *because* the driver is away. `route_stops` are **soft-deleted** (an assignment points at one, and a deleted stop must still be able to say what a rider was paying) and carry **the monthly fare** — distance is what a BD school charges for, so the fee is on the stop and never on the route; `uq_route_stops_order` makes the sequence real, which is why reordering is a two-pass write (the M11 renumber problem). `transport_assignments` key on **`enrollment_id`** and are a service **window**: `effectiveFrom = resumed_at ?? start_date`, `effectiveTo = end_date ?? suspended_at ?? open`, pinned by `chk_transport_assignments_window` and `chk_transport_assignments_status_evidence` (ENDED carries an end date, SUSPENDED a suspension date, and an ACTIVE row may **not** still carry one) — the M21 `exit_date` reasoning, because a status change with no date cannot answer "how much of March does this rider owe". `uq_transport_assignments_live` excludes only ENDED, so a **suspended rider still holds their seat**. The stop is pinned to its route by a **composite foreign key** `(route_id, stop_id) → route_stops(route_id, id)` — a single-column FK would accept a stop from another route, and the school would find out when the driver's sheet printed a child waiting at a corner the bus never passes. `vehicle_expenses` carry a nullable `odometer` (a toll receipt has no reading) and `chk_vehicle_expenses_shape` requires `amount > 0`. Full graph grows per module; see each module §3.

## 9. Authentication Flow

**Live since M02.** Login (email/phone + password, argon2id) → access JWT 15 min (in memory) + rotating opaque refresh 7/30 d (httpOnly `hs_refresh` cookie, path `/api/v1/auth`) → rotation with reuse-detection (reuse outside 5 s two-tab grace ⇒ revoke ALL sessions + SMS alert; rotation never extends the session window). **Since M09** one contact may back one account PER user type (a guardian who is also staff) — uniqueness is `(school_id, user_type, contact)`, and login verifies the password against EVERY candidate for the identifier (`UsersRepository.findAllByIdentifier`), a failed attempt counting against each unlocked one; OTP/reset target the oldest candidate until username login lands. OTP (6-digit, hashed, 5 min, 3 attempts, 60 s resend) for reset/verification; verify-otp mints a 10-min reset token. Lockout 5 fails/15 min (423). Generic errors everywhere (no account enumeration). Frontend: axios single-flight refresh interceptor → `/auth/refresh`; `proxy.ts` guards route groups via the `hs_session` hint cookie; forced-change interstitial when `must_change_password`. Bootstrap Super Admin comes from the seed (`admin@hexschool.local`).

## 10. Authorization Flow

**Live since M03.** RBAC: permission codes registry (TS code = source of truth, idempotently synced to `permissions`; removed codes orphan-flagged and denied) → roles (11 system roles seeded per school, non-deletable/non-renamable, core sets locked extend-only) → users (`user_roles`; every user keeps ≥1 role, last `super-admin` holder protected). `PermissionsGuard` + `@RequirePermissions()` (AND) / `@RequireAnyPermission()` (OR); permissions cached in Redis 5 min (`perm:{userId}`), invalidated on role change, DB fallback if Redis is down; Super Admin (`user_type`) bypasses. **Guard chain is pinned in `AppModule` providers (Throttler → JwtAuthGuard → PermissionsGuard) — global-guard order follows provider registration order, so never register APP_GUARDs from feature modules.** Role edits use optimistic concurrency (`expectedUpdatedAt` → 409). Frontend `<Can>`/`usePermissions()` + `ADMIN_MENU` permission-per-item config (UI gating only; API is authoritative). **Portals (M18) are authorized by OWNERSHIP, not permission codes** — the `OwnershipGuard` + `PortalResolverService` resolve the logged-in user to the student ids they own (student=self, parent=children via `student_guardians`, teacher=what they teach); `assertOwnsStudent` is the single IDOR chokepoint (a `@OwnsStudent('childId')` route 403s any other id, re-verified in the services). The admin/accountant dashboards ARE permission-gated (`dashboard.admin`/`dashboard.accountant`); the reports hub self-filters by permission.

**Audit (M03):** every successful mutating request writes an immutable `audit_logs` row via the global `AuditInterceptor`. New modules: set precise diffs from services via `AuditContextService.set({entityType, entityId, oldValues, newValues})`; use `@Audit({action})` for verb overrides and `@SkipAudit()` only for machine noise. `action` is VARCHAR — extend `AUDIT_ACTIONS` (both repos) instead of migrating an enum.

## 11. Global Business Rules

- One `is_current` academic session (DB partial unique index since M05); sessions never overlap in dates; COMPLETED sessions are read-only for entry flows — **enforced since M12** (attendance marking refuses a COMPLETED/ARCHIVED session; M15 marks entry must do the same). Activate rolls the demoted ACTIVE session to COMPLETED.
- One enrollment per student per session; roll unique per section.
- One attendance record per student per date (**per period since M13** — `period_id` has its FK and `attendance.mode = 'period'` turns it on; a `periodId` sent while the mode is `daily` is refused, not ignored); attendance may not be taken for a future date, outside its session, or on a holiday without `attendance.holiday.override`. Attendance % = `(present + late + ½ half-day) ÷ working days`, working days excluding holidays, weekly off-days and days before the student's `enrollment_date`.
- **Only PUBLISHED routines are portal-visible** (M13). One DRAFT + one PUBLISHED per section per session; publishing archives the version it replaces, so `effective_from` + `version` reconstruct any past date's routine. Drafts are deletable; published/archived versions are history.
- Published results/receipts/vouchers/certificates are immutable — corrections via reversal/reissue with audit trail. **Enforced since M15:** a LOCKED mark changes only through the correction flow (reason mandatory, `mark_corrections` written first), and a re-issue is publication version N+1 with a changelog note, never an edit of the live one.
- **Result visibility is the ACTIVE publication row, not `exams.status`** (M15). Unpublishing revokes the active version and hides the results everywhere without touching the computed numbers.
- **NCTB result rules** (M15): GPA is the mean of *grade points* over compulsory subjects; the optional (4th) subject adds only the points **above** `exam.optional_bonus_base` and never joins the divisor; one compulsory F is a fail with GPA 0.00; an optional F never fails anybody; a missed per-component pass threshold forces the failing grade regardless of the total. Merit is competition ranking (1, 2, 2, 4) among PASSED candidates only.
- A grade is a property of the **run**, not of the mark: `marks.grade`/`grade_point` are written only by a processing run, and re-entering or correcting a mark clears them.
- All money NUMERIC(12,2) BDT; every monetary override needs permission + reason.
- **Fees (M16):** an invoice's status is **derived, never assigned** (`fine.engine.ts` `deriveStatus`; `payable ≤ 0 ⇒ PAID`, so a fully-waived invoice is never late-fined); the monthly batch is idempotent per `(enrollment, month)`; a payment allocates **oldest-due-date-first**; a late fine is charged **at most once per calendar month**; a refund is refused against a non-refundable head and never exceeds what was paid; overpayment needs `fee.overpay`. **Online money is SUCCESS only after a server-side `verify()` whose amount matches ours** — a gateway callback is a hint, never a verdict — and a SUCCESS online payment must carry `verified_at` (`chk_payments_success_evidence`). Dues are read via `LedgerService.outstandingFor`, the single dues source for every gate (`EXAM_DUES_GATE` live).
- **Communication (M17):** every module-originated message goes through `NotificationService.send()` — no direct gateway calls. A message is rendered from a template (per code/channel/EN-BN, variables validated against a per-code allow-list), held out of **quiet hours** unless EMERGENCY, **deduped** on `(destination, template)` within a window (a DB partial unique; two absent siblings merge into one SMS), and **credit-accounted** per SMS part (a metered school's send is refused when it cannot cover the parts). SMS is real via a configurable BD-gateway adapter with a log-only fallback; the worker records SENT→DELIVERED/FAILED and a DLR webhook (secret-verified) closes the loop.
- **Portals (M18):** a portal user sees only what they OWN (student=self, parent=children via `student_guardians`, teacher=what they teach) and only PUBLISHED artifacts (published routine, active result publication, published notices) — enforced by ownership, not a permission code. Dashboards are cached best-effort in Redis and render zero-states for an empty school. Result-withhold-on-dues, portal Pay-Now and the dues-reminder blast are live here.
- **Website (M19):** only `PUBLISHED` content — and, for notices, `is_website_visible` — is served publicly; the filter lives in the repository's `published*` helpers so an endpoint cannot forget it. A draft is reachable only through a **signed token naming that exact row**, and a missing page, an unauthorised draft, a withheld student and a switched-off feature all return the **same** 404 — a public endpoint never confirms that something exists. Author markup is **sanitized on write** against an allow-list, so the stored row is the guarantee. `published_at` is derived, never assigned: first publish stamps it, re-publish and unpublish preserve it. Public writes (contact, career application, verification) carry reCAPTCHA + a route throttle, and the contact form adds a per-IP hourly cap.
- **Accounting (M20):** every POSTED voucher balances **exactly** (Σdebit = Σcredit to the paisa) and only **leaf** accounts may be posted to — a heading is a subtotal and would double-count. A POSTED voucher is **immutable**: the correction is `cancel()`, which writes a mirror-image reversal dated *today* (back-dating it would restate a month already signed off) and leaves both documents in the ledger — so the ledger predicate is **"every voucher that was ever posted"** (`posted_at IS NOT NULL`), never `status = 'POSTED'`. An **auto-posted voucher may never be hand-edited** — it is the machine's record of a real payment. Fee money posts itself on `payment.success` (Dr cash/bank/clearing, Cr fee income split per head by largest remainder so the two sides match exactly) and reverses on `payment.refunded`, idempotent on `source_ref`. **No posting into a CLOSED period** — except a backdated payment, which posts into the next open one *with a note* (roadmap §8, BD practice, `accounting.backdate_after_close`); closing refuses over a DRAFT dated inside the range; reopening needs `accounting.period.reopen` and a reason. Cash may not go negative (`HARD`/`SOFT`/`OFF`), and a voucher may not be dated further ahead than `accounting.future_voucher_days` (default 0). The Accountant keeps the books but holds neither `voucher.cancel` nor `accounting.period.reopen` — the M16 separation-of-duties rule.
- **HR & Payroll (M21):** leave costs **working days**, not calendar days, and consumes a **per-session** balance — approving decrements `used` inside the same transaction as the status flip, and withdrawing an APPROVED leave hands the days back (which is what `CANCELLED` is for: a person who withdraws is not a school that refused). An **UNPAID** leave type is never "over quota" — the days come out of pay, not an entitlement. A salary assignment is **history**: a change writes a new row from a date, never an edit, so regenerating March reads March's salary. **One live payroll run per month**; regeneration wipes and rewrites while DRAFT/GENERATED; an **APPROVED run is frozen** and corrections go on next month's run as an adjustment line (the M15/M20 immutability rule); a **DISBURSED** run cannot be cancelled. **HELD payslips** are excluded from the disbursement, the bank advice and the voucher until released. A day covered by approved leave is **never also an absence**, and an **unmarked** working day is treated as present — recording an absence is the register's job (the M15 "a missing mark is never a zero" rule). The provident fund follows the **pay scale**, not the attendance register. Net pay is non-negative **by construction** (the discretionary deductions absorb the remainder) rather than by a floor, so the payslip's lines keep adding up to its total and the salary voucher keeps balancing.
- **Assignments (M22):** a teacher may set, read and mark work only for the section-subjects they hold **right now** — the policy re-reads `teacher_section_subjects` at every request, so a reassignment moves the rights with it; `assignment.all` widens that to the school, and the original author keeps access to work they already marked. **Only PUBLISHED work is visible to a section**, and a draft read from the portal returns the same 404 a non-existent id gets (the M15/M19 rule that a read must not confirm what the caller may not see). A student submits only for **their own enrollment**, only to their own section, only late if `allow_late`, and **a parent may never submit** — reading their child's list is the whole of the parent's role here. A resubmission **replaces the row and clears the mark, feedback and evaluator**, because whatever was said about the old work no longer describes what is on file (the M15 "re-entry clears the grade" rule); an EVALUATED submission can only be reopened by the teacher's `return`, which requires feedback and clears the mark. Marks may not exceed `full_marks`, and `full_marks` may not be lowered below a mark already given. **CLOSED locks evaluation**, and the unlock is a separate code (`assignment.evaluate.override`) the Teacher baseline deliberately lacks. Deleting an assignment is refused once anybody has submitted — the FK cascades, so the school's route is to close it, not to erase what a class handed in (the M14/M15 "blocked once marks exist" guard). `is_late` is stored, never recomputed. Author HTML is sanitized on **write** through the M19 allow-list sanitizer.
- **Library (M23):** a copy must be AVAILABLE — or held **for this member** — to be issued, and ISSUED/LOST/DAMAGED/WITHDRAWN are **structural** refusals no permission reaches (the M13/M14 two-tier override split); over-limit, unpaid-fine, overdue-holding, suspended and duplicate-title are **policy** refusals `library.issue.override` may push past, recorded against a name. The unpaid-fine total spans **every** loan, returned or not — otherwise a habitual defaulter clears the block by handing everything back. All of those verdicts come from **one** `canIssue` call, so the greyed button, the 409 and the OPAC’s blocked reason cannot disagree. A **renewal is refused while the loan is overdue**, because renewing moves `due_at` and would erase a fine already earned; the new period runs from *today*. Overdue = chargeable days × rate, capped, with grace off the lateness and holidays off the chargeable days **in that order**. A lost or damaged copy is charged at price × multiplier, falling back to `library.default_book_price` (charging nothing for an unpriced book is how the unpriced half of a catalogue becomes the half that goes missing), and writing off a copy that is on loan **closes that loan** so the member’s slot is freed. `fine_paid` is derived; a collection may not exceed what is outstanding; a waiver carries a name and a reason. A returned copy somebody is waiting for is **held, not shelved**. Only AVAILABLE/RESERVED copies are expected at a stock-take, and the expectation is resolved at close. **The Librarian takes money and may not write it off** — `library.fine.collect` and `library.fine.waive` are different codes held by different people (the M16/M20/M21 rule).
- **Transport (M25):** a rider's assignment is a service **window**, not a status — suspending, resuming and ending each write a **date**, and M16 bills `[resumed_at ?? start_date, end_date ?? suspended_at ?? ∞)` intersected with the month. The transport line arrives at invoicing **already prorated** and must be added with `prorated: false`; proration by enrollment date and proration by service window answer different questions, and multiplying them bills a mid-month joiner (21/31)² of the fare. The fare lives on the **stop**, so a stop with riders on it may not be deleted (that would stop those families being billed silently) and a route split matches stops **by name** to preserve what a family pays. Over capacity **warns**; `transport.capacity_hard_block` makes it a policy refusal and `transport.assign.override` is what passes it — there is no structural seat rule, because a 40-seat bus carrying 41 children is a real thing and a system that made it unrecordable would be lied to. A **SUSPENDED rider still holds their seat**; only ENDED frees it. A route needs ACTIVE status and a vehicle before children go on it, but a vehicle in **MAINTENANCE passes** (the bus is back on Monday). A lapsed document is a **warning, never a refusal**, and a *missing* expiry date is not a valid one — it reports UNKNOWN and appears in the alert list. Vehicle spending posts to the ledger as a **DEBIT** voucher (the first auto-posted one that spends rather than receives), and a posted expense is not editable in place; deleting it leaves the voucher standing, because reversing a posted entry is the accountant's call (M20).
- Soft delete everywhere except append-only logs (audit, ledger, login activity, notifications, sms credits, **pf ledger**) and `voucher_entries` / `salary_components` (hard-deleted with their parent) — plus `assignment_submissions`, which has no `deleted_at` because it is replaced in place (M22).
- Timezone: store UTC, display Asia/Dhaka; weekly holiday configurable (default Friday).

## 12. Common Validation Rules

| The Librarian holds `library.fine.collect` and deliberately **not** `library.fine.waive` or `library.issue.override` | The person who takes the money is not the person who decides it is not owed, and the borrowing limits are the school’s policy rather than the desk’s. | Code 128 is hand-rolled rather than pulled from a library | The spec is small, completely specified and golden-testable against a check digit worked by hand — the `ics.util.ts` (M05), `feed.util.ts` (M19) and `zip.util.ts` (M22) precedent. | The overdue chase runs **daily** and decides for itself whether today is the configured weekday | `library.overdue_notice_weekday` is a per-school setting and one cron expression cannot be per-school — the M12 job convention, where the schedule is coarse and the settings decide. | **A transport assignment is a service WINDOW, not a status** | M16 has to answer "how much of March does this rider owe", and a status change with no date behind it cannot — the M21 `exit_date` lesson, applied before it could bite. | The stop, not the route, carries the monthly fare | Two children on one bus pay different amounts depending on how far they travel. | Over capacity **warns**; there is no structural seat rule | A 40-seat bus carrying 41 children is a real thing that happens in Bangladesh, and a system that made it impossible to record would simply be lied to. `transport.capacity_hard_block` turns it into a *policy* refusal and `transport.assign.override` passes it — the M13/M14/M23 structural-vs-policy split. | `uq_vehicles_reg_no` is scoped to LIVE rows, unlike employee IDs, student UIDs and accession numbers | Those are issued **by the school** and printed on something, so they are never reused. A registration plate is issued by the BRTA and belongs to the vehicle — a school that deletes a mis-typed row must be able to enter the same plate again | M25 |
| A missing expiry date reports UNKNOWN and appears in the alert list | The vehicle with no fitness date recorded is the single most likely one to be unfit. A truthy/falsy implementation would let exactly that row pass every check silently | M25 |
| Fleet distance comes from the **gaps between odometer readings** | `max − min` over a vehicle's history silently includes kilometres covered before the first receipt was entered, so cost-per-km comes out too low — the direction that makes a school keep an expensive bus. A reading that goes backwards breaks the chain rather than producing a negative distance, because meters are re-entered wrongly, replaced and rolled over | M25 |
| Deleting a posted transport expense does **not** cancel its voucher | `voucher.cancel` is a permission the transport desk does not hold, and silently reversing a posted entry from a fleet screen is exactly the quiet restatement M20 exists to prevent. The expense is soft-deleted and the accountant is told | M25 |

(1) Every canonical was emitted **relative** (`href="/"`) — `metadataBase` was set only when a school happened to fill in `website.site_url`, and Next leaves relative metadata relative without it, which a crawler rejects; the resolution chain now always ends somewhere absolute (configured domain → `NEXT_PUBLIC_SITE_URL` → localhost). (2) The public site called **`/auth/refresh` on every visit**, which for an anonymous visitor can only 401 — a wasted round trip on the critical path of the pages that most need to be fast, plus a console error on every marketing page; the bootstrap is now scoped to the authenticated route prefixes. SEO 92 → 100 and best-practices 96 → 100. **Run Lighthouse on a public surface before calling its SEO done.**
- **M19 (lesson, not debt):** the first k6 run measured **the throttler, not the server** — the public API allows 100 req/min/IP, so a single-origin 200 rps test 429s after the first second and reports flattering latencies on rejected requests. The script now varies `X-Forwarded-For` (the API runs `trust proxy` behind Nginx) to reproduce the many-households shape a result day actually has. Caveat on the numbers: one laptop hosted Postgres, Redis, the API, Next **and** an 800-VU generator, so 150 rps is a floor, not a production verdict — re-run on real infrastructure before sizing.
- **M19:** the public API resolves `DEFAULT_SCHOOL_ID` (the M10/M15/M16 precedent) — multi-tenant public routing is an M31 concern. `PublicSiteRepository.adminUserIds` repeats a query `AudienceRepository` (M17) already has, because that repository is CommunicationModule-private.
- **M19:** in-browser click-throughs pending: the gallery lightbox on a phone, a real CV upload to MinIO, the contact form with live reCAPTCHA keys, and a draft-preview link opened in a private window.
- **Cross-module (test isolation), fixed in M19:** `auth.service.spec.ts` (M02) failed intermittently — always on an argon2-hashing case, always with Jest's 5-second default timeout. argon2id is *deliberately* memory-hard and several cases there hash more than once, so 5 s is generous on an idle machine and tight when the other 84 suites compete for the same cores; growing the suite from 932 to 1030 tests is what surfaced it. The file now sets a 30-second budget with a comment explaining that the number is about the KDF's cost, not about the code under test. Pre-existing, not an M19 regression — five consecutive full runs are green.
- **Cross-module (tooling), found in M19 and raised again in M20:** the e2e suite needs an explicit heap — **`--max-old-space-size=6144`** at 19 suites, **`8192`** since M20 made it 20, together with a **60-second `testTimeout`** (was 30 s). With 19 Nest applications compiled in one `maxWorkers: 1` process, Node's default heap leaves the last suites starved — a *different* suite times out in `beforeAll` on each run, which reads like a flaky test and is not one. `npm run test:e2e` carries the flag; run it that way rather than bare `jest --config`. **M20 raised them again (6144 → 8192, 30 s → 60 s) — but as a precaution, not a proven necessity.** A run where `portal`, `communication` and `website` all timed out in `beforeAll` (48 of 49 failures) looked like the next rung of the same ladder; chasing it properly found a **polluted queue environment** instead (see the next entry). The raises are kept because they cost nothing and remove a class of misleading red. Expect to revisit around 24 suites; the durable fix is sharding the e2e run, which belongs to M30.
- **M20 (lesson, not debt):** the e2e suite found that every accounting report read `WHERE status = 'POSTED'` — the obvious predicate, and wrong. Cancelling a posted voucher sets it CANCELLED and writes a mirror-image reversal; that filter **dropped the original out of the ledger while keeping the reversal**, so a cancelled 25,000 receipt read as 25,000 of *negative* income and pushed cash to a credit balance. No unit test could see it (the engines never ask about status) and each report still looked internally consistent on its own — which is why the suite asserts **the three statements agree with each other**. Fixed to `posted_at IS NOT NULL` ("every voucher that was ever posted"), with the reasoning recorded on both repository methods. **When a status flag means "superseded" rather than "never happened", filtering on it silently rewrites history.**
- **M20:** auto-posting is **income-on-receipt**, per roadmap §4 — an invoice raised and unpaid never touches the ledger, so `1410 Fees Receivable` is seeded but unused. Accrual mode (Dr Receivable at invoicing, Cr it at payment) is a setting-gated follow-up; decide before a school's first full fiscal year.
- **M20:** roadmap §4's optional **closing entries** at period close (transferring income/expense into accumulated surplus) are not built — the close locks the period, and the balance sheet carries the surplus as a computed line instead.
- **M20:** the general ledger loads every posted entry in the window to build the "particulars" column (the other accounts on each voucher); push it into SQL when a school has a long history — the same caveat M13's conflict engine and M15's analytics carry. Budget-vs-actual rolls monthly lines into one row per account (no month-by-month grid yet).

- **Cross-module (latent fragility), found in M20:** M15's result processing loops a whole exam — every candidate × every paper, writing a grade per mark — inside **one** Prisma interactive transaction, against the library's **5-second default**. Crossing it does not fail loudly: Prisma kills the transaction mid-flight and the run is recorded FAILED with a Prisma internal message, which reads like a data problem and is not one. The M20 e2e run's twentieth suite added enough contention to push a 5.5-second run past it. `ResultsRepository.withTransaction` now takes an options argument and both bulk passes pass an explicit `{ timeout: 120_000, maxWait: 15_000 }`. **A transaction budget belongs to how much work the operation genuinely does, not to a library default chosen for short ones** — worth checking wherever a loop writes per row inside `$transaction`.

- **Cross-module (environment), diagnosed in M20 — read this before debugging a queue-dependent e2e failure:** a bare **`docker compose up -d` also starts the `backend` service**, which runs its own API against the same Postgres *and the same Redis*. Its BullMQ worker then **competes with the test process for jobs**, so a notification or a result-processing run is picked up by the container, never reaches its terminal status, and the suite reports "did not reach SENT in time" — indistinguishable from a code defect. `redis-cli flushall` against a live stack does the same damage from the other end (`[ioredis] Stream isn't writeable and enableOfflineQueue options is false`). **The tell:** only the two queue-dependent suites fail (`communication`, `result`), and a *different* subset each run. Measured: on a polluted stack `result.e2e-spec` took **130 s and failed 29 of 55**; after `docker compose down` + `docker compose up -d postgres redis minio mailpit` it is **55/55 in ~10 s**, and `communication` went 20/20 four runs running. Start the infra services **by name**. Documented in `hexschool-backend/test/README.md`.

- **M25 (lesson, not debt):** an e2e fixture ran `updateMany({ where: { enrollmentId: undefined } })` after an earlier failure left the id unset — and **Prisma reads an `undefined` filter as *no* filter**, so it ENDED every transport assignment in the database. The delete guards then passed (nobody was riding), the route was deleted, and eleven downstream assertions failed pointing everywhere except the cause. **An `undefined` in a Prisma `where` is not a narrow filter; in a test its blast radius is the whole table.** Assert fixture ids before using them in a bulk write.
- **Cross-module (test isolation), found in M25 — the third of its kind:** the transport e2e built its fixture dates from **UTC** while the server dates everything through `dhakaToday()` (UTC+6), so for **six hours of every day** (18:00–24:00 UTC) the two disagreed by one. The run that happened to cross midnight Dhaka failed three ways at once: a "40 days ago" expiry read as 41, an assignment created *today* was ended *yesterday* and `chk_transport_assignments_window` refused it, and the rider who therefore never ended still held a seat. The helper now shifts into Dhaka before slicing. **A suite that passes at 14:00 and fails at 19:00 is not flaky, it is wrong** — the M18 attendance-on-Friday and M23 `chk_book_issues_window` lessons, combined: never mix a client-side clock with a server-side one, in a row *or* in an assertion.
- **M25 (lesson, not debt):** the odometer "reading went backwards" warning never fired, because the service wrote the expense and *then* read the vehicle's history to compare against — which by then contained the new row, so it compared 9,000 with itself. The engine was correct throughout; the defect was in what the caller handed it, which is precisely the class of bug a unit test on the engine cannot see and an e2e assertion on the warning text can.
- **Cross-module (environment), a SECOND cause found in M23 — read this beside the M20 entry above:** the first full e2e run failed 12 cases across exactly `communication` and `result`, the documented polluted-stack signature. The `backend` container was **not** running this time; the cause was an **orphaned jest process from an earlier run that had been killed**, whose Nest apps’ BullMQ workers were still connected to the same Redis and eating jobs. Killing it took the suite to **644/644 on the next run with no code change**. The tell is unchanged — only those two suites, a different subset each time — so the check is now: `docker compose ps` for a stray `backend`, **and** `Get-Process node` / `ps` for a stray jest.
